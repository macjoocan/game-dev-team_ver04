## [기준]

공통 원화는 `out/2d-gpt-20261106/silver-swordswoman-gpt-v1.png`다. sprite-gen으로 512×512 캔버스에 맞췄다. 최대 피사체 높이 432px, 기준선 y=480, 8프레임·8 FPS로 비교했다. 실제 게임 화면 크기는 아직 정하지 않았으며 128px·256px는 검수용 표시 크기다.

검수 축은 손·손잡이·칼날의 연결, 칼의 강체 유지, 포니테일·망토·부츠 보존, 다리 교차, 발 접지, 마지막 프레임과 첫 프레임의 연결이다. 원본 프레임을 먼저 검사했다. 별도의 정규화·아틀라스 결과로 원래의 위치 흔들림을 숨기지 않았다.

소스는 다음 커밋으로 고정했다. 원본 파일은 수정하지 않았다.

- sprite-maker `9de73a6136a1a045af2e8769349fbadc17dbef69` (MIT)
- sprite-gen `4f5ccd55c7cf06685a41f954acc1e476b7772ece` (Apache-2.0)
- 작업 저장소 HEAD `4c43b68`, 기존 미커밋 변경이 있는 상태

A는 `types.rs`·`ik.rs`·`mesh.rs`·`skin.rs`를 그대로 포함하는 작은 Rust 파일 입출력 어댑터로 실행했다. 앱·DB와 연결하지 않는 타입만 호환 선언으로 대체했다. 관절 위치 21개, 뼈 15개와 발 목표는 이 실험에서 작성했다. 자동 관절 추천을 시험한 것은 아니다.

처음 설정한 보폭은 한쪽 다리의 도달 범위를 넘었다. 초기 자료는 `archive-rig-v0/`에 보존했다. 보폭을 줄인 뒤 발목 목표 오차가 사라졌지만 칼 휨은 남았다. 강체 분리 검사는 같은 소스의 `render_frame_with_mesh(..., None)` 분기를 직접 호출했다. 앱의 기본 설정을 바꾼 것이 아니다.

B는 내장 `image_gen`으로 원화 참조 시트를 한 번 생성했다. sprite-gen의 생성 공급자 CLI는 호출하지 않았다. 실제 사용한 sprite-gen 기능은 `slice-sheet`, 알파 정리, `inspect-motion`이다. Grok·외부 영상 API·ComfyUI는 이번 비교에 사용하지 않았다.

## [공백]

- B 생성은 한 번뿐이다. 두 방식은 동일 시드나 동일 관절 포즈를 강제할 수 없어, 같은 원화·프레임 수·출력 규격을 맞춘 비교다.
- sprite-maker 전체 데스크톱 앱, 자동 리깅, 별도 파츠 원화를 쓰는 렌더링, AI polish는 검사하지 않았다. 이번 실패를 모든 리깅 방식에 일반화하지 않는다.
- B의 0~3번을 같은 발의 접지 구간으로 가정해 x=210, y=464, w=200, h=16 영역을 측정했다. 도구가 이 가정을 검증하지 못했다. 실제 발 미끄러짐 속도나 이동 속도는 아직 모른다.
- `inspect-motion`의 exit 0은 보고서 생성 성공이다. 접지·걷기·반복 경계 통과가 아니다. 반복 경계의 자동 통과 판정은 하지 않았다.
- 페이지에서 프레임 로드, 재생·정지, 프레임 이동, 밝고 어두운 배경과 크기 변경을 확인했다. 실제 엔진·전투 화면은 검사하지 않았다.
- 기존 art-gate는 샘플 경로가 없어 측정 불가다. [시작 로그](art-gate-start.log)를 남겼다. `docs/pipeline/state.json`도 없어 열린 게이트는 미확인이다.
- 새 도구의 전역 설치·플러그인 배포·원격 push는 하지 않았다. 생성 이미지의 최종 사용 권리와 사람의 출하 승인은 이번 범위 밖이다.

## [잔여 위험]

B를 후속 기준으로 삼는다. 먼저 02·06번의 무릎 통과 자세, 07→00 반복 경계, 검을 쥔 손의 위치 변화를 작은 화면에서 검수한다. 발 접지의 가정이 성립하지 않은 상태로 이동 속도를 자동 계산하지 않는다.

리깅을 다시 시도한다면 검을 독립된 강체 이미지로 만들고, 가려진 다리·몸통까지 채운 파츠 원화가 필요하다. 이번 한 장 자동 분리 결과는 그 준비를 대신하지 못했다. 공용 도구나 스킬로 자동 승격하지 않는다.
