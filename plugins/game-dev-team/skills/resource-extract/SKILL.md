배포 빌드에서 게임 데이터를 꺼내 **구조를 읽을 수 있는 형태**로 만든다. 레퍼런스 트랙(R)의 입구다.

## R0 — 시작하기 전에 사람이 확인할 것 (통과 못 하면 진행 금지)

이 단계는 스킵하지 않는다. 오케스트레이터가 사람에게 물어 답을 받은 뒤 시작한다.

| 확인 | 통과 조건 |
|---|---|
| 목적 | 사내 리서치·구조 분석·설계 참고. **제품에 그대로 넣기 위한 추출이 아니다** |
| 대상 | 정상 경로로 받은 빌드. 유출본·크랙본 아님 |
| 기술적 보호조치 | **암호화·DRM·안티탬퍼가 걸려 있으면 여기서 멈춘다.** 우회는 법무 확인 전에는 하지 않는다 |
| 배포 범위 | 추출물은 사내 분석용. 외부 공유·재배포하지 않는다 |
| 산출물 격리 | 추출물은 `_reference/` 아래에만 둔다. 프로덕션 경로에 섞지 않는다 |

`codec: auto`가 푸는 **압축·인코딩**(gzip·base64·hex 등)은 보호조치가 아니라 저장 포맷이므로 여기 해당하지 않는다. 반면 키가 필요한 `xor:` / `aes_cbc:` 스텝을 써야 하는 상황이면 **R0로 되돌아가 사람 판단을 받는다.**

## 도구

`levelscope` — APK/XAPK/OBB/폴더에서 레벨·팔레트·스프라이트·에셋·씬 계층을 뽑는 파이프라인.
**설치 위치는 플러그인이 아니라 프로젝트 `CLAUDE.md`에 적는다**(장르·환경 특화 정보를 플러그인에 하드코딩하지 않는다는 원칙). 없으면 사람에게 경로를 묻는다.

```bat
py -m levelscope survey  --input <apk> --configs configs     :: 처음 보는 게임: 뭐가 어디 있는지 + 설정 초안
py -m levelscope ls      --input <apk>                       :: 내부 경로 훑기
py -m levelscope detect  --input <apk>                       :: 인코딩 감지
py -m levelscope inspect --config configs\<game>.yaml --input <apk>
py -m levelscope run     --config configs\<game>.yaml --input <apk> --out out --limit 20
py -m levelscope assets    --input <apk> --out out           :: 사운드·머티리얼·폰트·Spine·텍스트
py -m levelscope hierarchy --input <apk> --out out           :: 씬·프리팹 GameObject 트리
```

## 절차

1. **처음 보는 게임이면 `survey`부터.** 설정 없이 던지면 위치·포맷을 보고하고 설정 초안까지 만든다.
2. `detect`로 인코딩을 확정한다. 여기서 암호화가 나오면 **R0로 되돌린다.**
3. `template.yaml`을 복사해 게임 설정을 만든다. `codec: auto`, `fields: auto`로 시작하고, `inspect`로 실제 JSON을 보며 board·fields를 채운다.
4. `run --limit 20`으로 앞 20개만 돌려 구조를 확인한 뒤 전체를 돌린다.
5. 레벨과 무관한 리소스(`assets`·`hierarchy`)는 설정 없이도 바로 뽑는다.
6. 게임 고유 로직(슈터 큐·타일 스택 등)이 필요하면 `plugins/<game>.py`로 분리한다. **코어를 게임에 맞춰 고치지 않는다.**

## 산출물 (게임당 6종)

| 파일 | 내용 |
|---|---|
| `<게임>_summary.xlsx` | Levels 시트 + 엔티티 시트 + Summary(세트·난이도·기믹 집계, 수식) |
| `<게임>_viewer.html` | 단일 파일 오프라인 뷰어. **이게 R6 정합성 검증의 기준 화면이 된다** |
| `<게임>_levels_decoded.zip` | 평문 JSON 원문 + `palette.json` |
| `<게임>_sprites.zip` | 스프라이트·텍스처 PNG |
| `<게임>_assets.zip` | 사운드·머티리얼·폰트·Spine·텍스트 + manifest.json |
| `<게임>_hierarchy.zip` | 씬·프리팹 트리 JSON + index.json |
| `<게임>_errors.txt` | 실패가 있을 때만 |

## 기준치 — 재추출은 반드시 대조한다

첫 추출 때 `_reference/<게임>/baseline.md`에 아래를 적어 둔다. 다음 추출은 이 표와 대조한 결과를 함께 보고한다.

- 레벨/에셋 **개수**(세트별로 나눠서) · **디코딩 실패 수**(0이어야 한다)
- 엔티티 행 수 · 팔레트 색 수 · 난이도 분포
- 대상 빌드의 **버전·파일 해시**, levelscope **버전**

**수치가 크게 다르면 추출이 실패한 게 아니라 게임이 업데이트된 것이다** — `detect`/`inspect`부터 다시 한다. 이걸 구분하지 않으면 바뀐 구조를 "추출 버그"로 오진한다.

## 보고 (검증 리포트 5섹션)

`ORCHESTRATION.md §5`를 따른다. 이 스킬에서 **증거**로 인정되는 것:

- 실제 실행한 명령과 출력
- 대상 빌드의 **버전·해시**, levelscope **버전**, 설정 파일 경로
- 기준치 대조표(항목 / 기준 / 이번 / 차이)
- 실패 목록(`errors.txt`) 또는 "실패 0"

세지 않은 것을 "이상 없음"으로 넘기지 않는다. 못 뽑은 카테고리는 **공백** 칸에 적는다.

## 게이트 R1 → R2

사람이 승인해야 다음(정합성 검증)으로 간다. 승인 조건: 산출물 6종이 생성됐고, 기준치 대조표가 있고, 디코딩 실패가 0이거나 실패 사유가 파일별로 설명된다.

## 하지 않는 것

- 암호화·DRM 우회 (R0에서 멈춘다)
- 추출물을 프로덕션 경로·빌드에 반입 (`unity-port` R7 소관)
- 게임성 판단 — 재밌는지는 `balance-sim`, 스펙 정확성은 `qa`
- 코어 파이프라인을 특정 게임에 맞춰 개조 (게임 고유 로직은 `plugins/`로)
