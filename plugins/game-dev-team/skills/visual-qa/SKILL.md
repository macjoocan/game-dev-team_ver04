# 시각 QA

아트를 프로덕션에 받아들이기 전, 또는 시각 패스를 "완료"라고 부르기 전에 쓴다.

## 검수 렌즈
| 렌즈 | 볼 것 |
|---|---|
| **가독성** | 실루엣, 대비, 실제 표시 크기, 중요한 액션이 보이는가 |
| **일관성** | 팔레트, 재질, 선 굵기, 카메라 앵글, UI 톤 |
| **기술** | 알파 정리, 크롭, 피벗, 압축, 아틀라스 배치, 명명 |
| **애니메이션** | baseline, 타이밍, 타격 프레임, 예비동작, 회복, 떨림 |
| **UI** | 텍스트가 들어가는가, 세이프에어리어, 겹침, focus/hover/disabled 상태 |
| **접근성** | 색만으로 주는 신호, 대비, 모션 강도, 작은 글자 |

## 증거
스크린샷이나 프리뷰 시트를 이 조건에서 남긴다:
- 실제 게임플레이 크기.
- 모바일 또는 가장 작은 목표 뷰포트.
- UI가 다 떠 있는 바쁜 전투/상태 화면.
- 해당되면 라이트/다크 또는 맵 배경 위.

여러 장을 한 번에 볼 땐 `art-direction`의 `contact-sheet.mjs`로 격자 한 장으로 합치면 빠르다.

## 도구 — 색각이상은 눈으로 판정할 수 없다

위 접근성 렌즈의 "색만으로 주는 신호"를 기계로 판정한다. 의존성 0(PNG 전용).

```bash
node skills/visual-qa/scripts/cvd-check.mjs <palette.json> [--pairs pairs.json] [--out dir]
node skills/visual-qa/scripts/cvd-check.mjs <palette.json> --image screen.png --out dir
```

`art-direction`의 `palette.json`에서 **의미가 다른 색쌍**을 뽑아 4가지 색각이상
(적색맹·녹색맹·청색맹·전색맹)으로 시뮬레이션한 뒤 구분 가능성을 잰다.
`--image`를 주면 실제 스크린샷을 4종으로 변환해 눈으로 볼 수 있게 낸다.

**왜 원본에 WCAG 명암비만 재면 안 되나**: WCAG 대비는 3색형 관찰자 기준으로 정의된 값이라
CVD로 그대로 변환되지 않는다. 올바른 순서는 **시뮬레이션한 뒤 재는 것**이다. 그리고 명암비는
밝기 차이만 보므로 "빨강 vs 초록"처럼 밝기가 같고 색만 다른 쌍의 붕괴를 못 잡는다 —
그게 정확히 적/녹색맹이 겪는 문제다. 그래서 **CIE Lab 색차(dE)**를 함께 본다(기준 10 이상).

붕괴하는 쌍이 나왔을 때 고치는 방법은 둘 중 하나다:
1. **명도를 벌린다** — 색상만 다르면 붕괴한다. 밝기 차이는 모든 유형에서 남는다.
2. **색 아닌 신호를 붙인다** — 형태·아이콘·패턴·텍스트. 팔레트를 안 고치고도 해결된다.
   이쪽이 접근성 원칙("색을 유일한 지표로 쓰지 않는다")에 더 맞고, 그 판정은 **사람이 한다.**

- 시뮬 행렬은 완전 이색형 근사(심각도 1.0)라 **하한 점검**이다. 통과해도 안심은 아니다.
- **녹색맹이 압도적으로 흔하다**(남성 약 6%, 적색맹 2%). 하나만 고칠 여력이면 거기부터.
- 동봉 starter 팔레트도 이 검사로 결함이 나와 고쳤다 — `danger`가 `primary.base`와 휘도가
  겹쳐 전색맹에서 dE 4.1로 붕괴했다.

## 도구 — 적 캐릭터가 서로 구분되는가

캐스팅이 늘면 "각자 잘 그려졌는가"와 별개로 **게임 크기에서 서로 구별되는가**가 문제가 된다.
크게 보면 다른데 64px 로 줄이면 같은 덩어리로 보이는 일이 실제로 생긴다.

```bash
node skills/visual-qa/scripts/cast-distinct.mjs <캐릭터.png>... [--sizes "[64,96]"] [--cvd]
                                                [--min-de 12] [--max-iou 0.72] [--out dir]
```

두 축을 따로 재고 **둘 중 하나만 통과하면 된다**:

1. **색차** — 평균색 dE 와 지배색 dE 중 큰 값. 색이 다르면 실루엣이 닮아도 구분된다.
2. **실루엣 IoU** — bbox 정규화 마스크의 겹침. 형태가 다르면 색이 닮아도 구분된다.

둘 다 미달인 쌍만 실패로 낸다. 한쪽만 보면 멀쩡한 캐스팅을 반려한다 —
같은 색 계열이라도 실루엣이 다르면 플레이어는 구분한다.

`--cvd` 를 주면 색차 축을 색각이상 시뮬레이션 뒤에 잰다. 색으로만 구분되던 쌍이
여기서 무너지면 실루엣이나 형태 신호를 더해야 한다.

- **줄여서 재라.** `--sizes` 는 실제 렌더 크기를 준다. 원본 512px 에서만 재면 의미가 없다.
- 실패 쌍이 나왔을 때 색을 바꾸는 것보다 **실루엣을 벌리는 쪽이 대개 싸다**(모자·무기·체형).

## 아트 게이트 전체를 한 번에

개별 도구를 따로 돌리는 대신 통합 판정을 쓸 수 있다. **두 하네스(Claude Code·Codex)가
같은 명령을 돌리므로 판정이 비교 가능하다** — 공동 컨트롤의 표면이다.

```bash
node <플러그인>/scripts/art-gate.mjs --init          # art-gate.json 생성 (프로젝트에 커밋)
node <플러그인>/scripts/art-gate.mjs --out art-out   # CVD·오버플로·회귀·규격·예산
```

리포트에 **어느 하네스·어느 커밋**에서 돌렸는지가 박힌다. 설정되지 않은 검사는 건너뛰고
**[공백]에 남는다** — 건너뛴 건 "문제없음"이 아니라 "모른다"다.
상세: `ORCHESTRATION.md` §10.

## 통과/반려
문제가 **고쳐졌거나**, 사람 소유자가 **명시적으로 감수**했을 때만 통과다.
미해결 항목은 에셋 ID · 스크린샷 · 심각도 · 담당을 붙여 기록한다.
색 판정은 `cvd-check`가 하고, **형태·아이콘 대체 신호가 있는지는 사람이 본다.**

## 흔한 실수
| 실수 | 교정 |
|---|---|
| 에셋을 따로 떼어놓고만 봄 | 실제 게임플레이 맥락에서 본다 |
| 한국어 텍스트 길이를 안 봄 | 대표적인 실제 번역 문자열로 테스트한다 |
| 자잘한 알파 결함을 넘김 | 대비되는 배경 위에서 확인한다 |
| 증거 없이 "시각 폴리싱 완료" | 스크린샷·콘택트 시트를 붙인다 |
| 용량·메모리를 시각 검수로 대체 | 그건 `asset-budget` 축이다. 여기선 판정하지 않는다 |

## 이 레포에서의 위치
- **소유**: artist + qa. 파이프라인 ⑦ 아트 단계의 **출구 게이트**.
- 검증 축이 셋 다 다르다: **정확성**(qa) · **재미**(balance-sim) · **보이는 것**(이 스킬).
  겹치지 않으므로 서로를 대신하지 못한다.

### 증거 규칙 (ORCHESTRATION.md §5)
"시각 폴리싱 완료"는 **증거 없이 말하지 않는다.** 스크린샷 없이 통과시키면 그건 판정이 아니라 인상이다.
- 실제 게임 화면 · 가장 작은 목표 해상도 · UI가 다 떠 있는 바쁜 전투 화면에서 각각 남긴다.
- 미해결 항목은 **에셋 ID · 스크린샷 · 심각도 · 담당**을 붙여 기록한다.
- 스크린샷을 못 만들었으면 판정은 통과가 아니라 **측정 불가**다.
