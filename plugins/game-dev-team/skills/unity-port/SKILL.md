추출본을 **실제로 돌아가는 유니티 프로젝트**로 옮긴다. 목적은 데이터 구조가 맞는지, 보드가 재현되는지를 화면에서 확인하는 것이다. 게임을 완성하는 단계가 아니다.

## 전제

- **R2(데이터 정합성) 통과.** 레벨 JSON이 몇 개이고 실패가 0이라는 게 확인된 뒤에 시작한다. 안 맞는 데이터를 이식하면 이식이 틀린 건지 데이터가 틀린 건지 구분할 수 없다.
- Unity 6.x 설치. `port_compile_check`가 설치된 어셈블리를 참조한다.

## 도구 — PortKit MCP

붙어 있으면 이 순서로 쓴다. 없으면 아래 "MCP 없이"를 따른다.

| 순서 | 도구 | 하는 일 |
|---|---|---|
| 1 | `port_init_project` | 유니티 프로젝트 뼈대 + 앱 골격 15파일. **씬 없이도 실행된다**(RuntimeInitializeOnLoad) |
| 2 | `port_add_game` | `IIngameFlow` 구현 스텁 + 부트스트랩. 규칙은 비어 있고 자리만 잡는다 |
| 3 | `port_import_palette` | levelscope config(yaml)의 `static:` 팔레트 → C# 클래스. **레벨의 색은 인덱스라 이 표만 있으면 스프라이트 없이 보드를 그린다** |
| 4 | `port_import_levels` | 레벨 zip에서 JSON을 골라 `StreamingAssets/Levels`로. 처음엔 `limit` 작게 |
| 5 | `port_compile_check` | 유니티를 열지 않고 dotnet으로 컴파일 검사 — 왕복을 줄인다 |
| 6 | `port_check_flow` | PlayMode 콘솔 로그를 넘겨 `Boot→…→Result` 완주 여부 판정 |

6번이 중요한 이유: **컴파일 0 · 콘솔 에러 0이어도 버튼이 안 먹으면 아무 일도 일어나지 않는다.** 에러가 없다는 것과 흐름이 돈다는 것은 다른 주장이다.

### MCP 없이

같은 순서를 손으로 한다: 프로젝트 생성 → 부트스트랩 진입점 → 팔레트 C# 상수화 → `StreamingAssets`에 JSON 복사 → 빌드 → PlayMode 로그 확인. 순서와 게이트는 동일하다.

## 이식 규칙

1. **레벨은 코드가 아니라 데이터로 들어간다.** JSON을 `StreamingAssets`에 두고 런타임에 읽는다. 레벨 수치를 C#에 박지 않는다(밸런스 하드코딩 훅이 경고한다).
2. **처음엔 아트 없이 그린다.** 팔레트 인덱스 + 단색 사각형으로 보드를 세운다. 원본 스프라이트를 붙이는 건 재현이 맞는 걸 확인한 다음이다.
3. **원본 에셋은 `_reference/` 안에서만.** 추출한 스프라이트·사운드를 프로젝트에 넣더라도 `Assets/_reference/` 아래 격리하고, `asset-pipeline` manifest에 **출처·라이선스·승인 상태**를 적는다. 승인 안 된 에셋은 프로덕션 씬·프리팹·빌드에 들어가지 않는다.
4. **표본부터.** `limit 10~20`으로 세트별 표본을 먼저 이식한다. 전량 이식은 R6 정합성이 통과한 뒤에.
5. **레벨 번호는 세트를 담지 못한다 — `pattern`으로 세트를 고정한다.** `port_import_levels`는
   `levels/<세트>/<번호>.json`을 `Levels/<번호>.json`으로 평탄화하므로, 같은 번호가 여러 세트에
   있으면 **어느 세트가 들어올지 통제되지 않는다.** 실측(PixelFlow 2026-08-20): 2,100개 번호 중
   **221개가 여러 세트에 중복**이었고, 표본 5개 중 2개가 `isValid=false`인 변형(AB테스트) 세트에서
   들어와 있었다. 컴파일 0·실행 정상이라 어떤 검사도 잡지 못한다. 반드시 `pattern`으로 메인 세트
   경로를 지정하고, 여러 세트를 함께 쓸 거면 목적지를 세트별로 나눈다.
6. **원본 구조를 그대로 베끼지 않는다.** 이식 대상은 *데이터*(레벨 배치·난이도 곡선)이고, 게임 코드는 우리 구조로 새로 쓴다.

## 절차

1. `port_init_project` → 빈 프로젝트가 실행되는지 먼저 확인한다.
2. `port_add_game`으로 플로우 스텁을 만든다.
3. `port_import_palette` → 색이 화면에 나오는지 확인.
4. `port_import_levels --limit 20` → 보드가 그려지는지 확인.
5. `port_compile_check` → 에러 0.
6. PlayMode 실행 후 콘솔 로그를 `port_check_flow`에 넘겨 완주 판정.
7. 결과를 5섹션 리포트로 보고하고 **R5 게이트**에 올린다.

## 보고 (검증 리포트 5섹션)

- **주장**: 충족 / 미달 / 측정 불가
- **증거**: 실행한 도구 호출과 출력, **이식한 레벨 수·대상 커밋·유니티 버전**, PlayMode 로그 원문
- **기준**: 원본 추출본의 레벨 수·팔레트 색 수(= `resource-extract` baseline)
- **공백**: 이식하지 않은 세트·포맷(예: random 포맷, board v2), 확인 못 한 화면
- **잔여 위험**: 표본만 이식한 상태에서 전량으로 늘릴 때 깨질 수 있는 지점

로그를 못 얻었으면 판정은 미달이 아니라 **측정 불가**다 — 되돌아가는 곳이 하네스(실행 환경)다.

## 게이트

- **R5 (이식 실행 확인)**: 컴파일 0 · 플로우 완주 로그 · 표본 레벨이 화면에 뜸
- **R7 (에셋 교체) — 출시·배포 경로로 나가기 전 반드시**: 추출 원본 에셋이 프로덕션 경로에 하나도 없어야 한다. 자체 제작·라이선스 확보 에셋으로 교체하고 `asset-pipeline` manifest로 증명한다. 판정은 artist + qa가 함께 한다.

## 하지 않는 것

- 원본 게임의 코드를 디컴파일해 옮기기 — 이식 대상은 데이터다
- R7 전에 추출 에셋을 프로덕션 씬·빌드에 반입
- 재미 판정(`balance-sim`)·정확성 판정(`qa`) — 여기서는 **돌아가는가**만 본다
