아트가 서비스에서 문제를 일으키는 방식은 대개 "안 예쁘다"가 아니라 **앱이 커지고, 메모리가 넘치고, 저사양 기기가 뜨거워지는 것**이다. 그리고 이건 다 만든 뒤에는 되돌리기 가장 비싼 종류의 문제다. 그래서 만들면서 잰다.

## 이 스킬의 전제 두 가지

1. **예산은 타깃 기기에서 나온다.** "텍스처 메모리 300MB"가 큰지 작은지는 최저 사양을 정해야 답이 된다. 타깃을 안 정했으면 그것부터 사람에게 확인한다 — 이 단계를 건너뛰면 나머지 숫자는 전부 의미가 없다.
2. **총량보다 증가율이 먼저 잡힌다.** 어느 날 갑자기 400MB가 되는 게 아니라 매주 12MB씩 는다. 그래서 **매 측정마다 직전 baseline과의 델타**를 함께 낸다.

## 예산 항목

| 항목 | 왜 보나 | 흔한 사고 |
|---|---|---|
| **배포 용량** | 스토어 다운로드 이탈 · 셀룰러 다운로드 한도 | 원본 해상도 PNG를 그대로 넣음 |
| **텍스처 메모리(VRAM)** | 저사양 OOM 강제종료 | 압축 미적용(RGBA32)이 몇 장 섞임 |
| **아틀라스 점유율** | 낭비 = 그대로 메모리 | 투명 여백이 절반인 스프라이트 |
| **드로우콜 / SetPass** | 발열·프레임 저하 | 머티리얼이 스프라이트마다 다름 |
| **셰이더 배리언트** | 빌드 시간 + 첫 로드 끊김 | 키워드 조합 폭발 |
| **오디오** | 용량의 숨은 절반 | 전곡 비압축·메모리 로드 |
| **폰트/아틀라스 SDF** | 글리프 커버리지 + 용량 | 한중일 전체 글리프 포함 |

## 측정 (Unity 기준 — 다른 엔진은 같은 항목을 그 엔진 도구로)

**엔진을 열지 않고 먼저 잴 수 있는 것**부터 한다. 왕복이 없다.

```bash
node <플러그인>/skills/asset-budget/scripts/scan-textures.mjs <프로젝트>/Assets
node <플러그인>/skills/asset-budget/scripts/scan-textures.mjs <프로젝트>/Assets --baseline budget-baseline.json
```
`.meta`의 임포트 설정과 PNG 헤더만 읽어 **압축 미적용 · 과대 해상도 · 4의 배수 아님(ASTC 불가) · 밉맵 낭비 · 추정 VRAM**을 낸다. Unity·유료 도구 없이 돈다.

엔진을 열어야 하는 것:
- 실제 빌드 용량 — Build Report (`Editor.log`의 Build Report 절)
- 런타임 메모리 실측 — Memory Profiler 스냅샷
- 드로우콜/SetPass — Frame Debugger 또는 Stats 창
- 셰이더 배리언트 수 — 빌드 로그

## 판정

`ORCHESTRATION.md §5`를 따른다. 항목별로 **충족 / 미달 / 측정 불가**를 따로 낸다 — 하나로 뭉뚱그리면 어디를 고쳐야 할지 사라진다.

| 판정 | 뜻 | 되돌림 |
|---|---|---|
| 충족 | 예산 안 | 다음 단계 |
| 미달 | 쟀고 넘음 | **아트(artist)** — 해상도·아틀라스·포맷 조정. 큰 것부터 |
| 측정 불가 | 빌드 리포트가 없거나 · 타깃 기기 미정 · 프로파일러를 못 돌림 | **개발/사람** — 잴 수단부터 만든다 |

"조금 넘었지만 괜찮아 보임"은 판정이 아니다. 넘었으면 미달이고, 넘겨도 되는 이유가 있으면 **사람이 예산을 고쳐 승인**한다(그리고 baseline에 기록한다).

## 보고 (검증 리포트 5섹션)

- **주장**: 항목별 판정 표
- **증거**: 실행한 명령과 출력, **대상 커밋·빌드 타깃·측정 도구**. 스캔 결과 상위 N개(무엇이 얼마나)
- **기준**: 타깃 기기와 예산표의 출처(문서 위치). 이전 측정이면 그 커밋
- **공백**: 못 잰 항목(예: "런타임 메모리 미측정 — 실기 없음")
- **잔여 위험**: 지금은 통과지만 이 속도로 늘면 언제 넘는지

델타를 반드시 넣는다: `현재 / 직전 / 증가분 / 남은 여유`. 증가분이 큰 항목 3개를 앞에 둔다.

## 게이트

- **⑦ 아트 출구**에서 `visual-qa`와 **함께** 판정한다. 보이는 것(visual-qa)과 감당 가능한가(asset-budget)는 다른 축이라 둘 다 필요하다.
- 실서비스 프로젝트는 **마일스톤마다** 재측정하고 baseline을 갱신한다.
- 에셋이 대량 추가되는 PR에서는 스캔만이라도 돌려 델타를 확인한다.

## 하지 않는 것

- 아트 품질·톤 판정 (`visual-qa`·`art-direction` 소관)
- 사람 승인 없이 에셋을 압축·축소해 덮어쓰기 — **원본(`_source/`)은 건드리지 않는다**
- 코드 성능 최적화 일반 — 여기서 보는 건 아트가 만드는 비용이다
