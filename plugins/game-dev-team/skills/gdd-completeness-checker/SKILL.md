기획 문서를 "개발이 질문 없이 착수할 수 있는 상태"인지 검사한다.
소유자는 game-designer(core)와 meta-economy-designer(경제)다. **수치를 임의로 채우지 않는다** —
빈 곳은 채우는 게 아니라 미결로 드러내는 것이 이 스킬의 일이다.

## 절차

### 1. 대상 수집
`docs/`·`design/`·CLAUDE.md·기획 문서 경로에서 GDD, 밸런스 표, 경제 원장을 모은다.
어떤 문서가 정본인지 모호하면 먼저 묻는다(잘못된 문서를 검수하면 게이트 자체가 무의미).

### 2. 필수 섹션 커버리지
없으면 "누락"으로 잡는다. 있는데 비어 있으면 "공란"으로 따로 잡는다.

| 섹션 | 있어야 할 것 |
|---|---|
| 비전 | 2~4문장. "무슨 게임이고 왜 재밌는가" |
| 코어 루프 | 1회 루프의 시작→선택→결과→보상이 한 바퀴로 서술 |
| 핵심 메커니즘 | 규칙·입력·상태 전이. 예외/실패 상태 포함 |
| 밸런스 수치 | 표로. 각 행에 근거 열 |
| **게임성 성공 지표** | **숫자로**. 목표 승률 구간·평균 런 길이·선택 밀도·사망 분포·픽률 편중 허용치 |
| 진행/난이도 곡선 | 구간별 의도 |
| 아트·오디오 방향 | 톤 한 줄 + 레퍼런스 |
| 리스크 | 이 기획을 침몰시킬 수 있는 것 + 완화책 |
| 마일스톤 | 무엇이 되면 다음 단계인지 |
| (경제 문서면) 재화 원장 | 소스/싱크 표, 확률·천장, 가격 |

### 3. 수치 감사 — 근거 등급
문서의 모든 수치에 등급을 매긴다. **C 미만은 전부 "미결"로 강등한다.**

| 등급 | 의미 |
|---|---|
| A | 공식/계산으로 유도됨 (유도 과정이 문서에 있음) |
| B | 선행 사례·레퍼런스 인용 (출처 명시) |
| C | 플레이테스트·시뮬 실측 (측정 조건 명시) |
| **없음** | 근거 문장이 없음 → **미결로 강등** |

"대략", "정도", "적당히", "추후 조정", "TBD", "??", 빈 셀, 주석 처리된 수치는 자동으로 근거 없음.

### 4. 미결 감사
숨은 미결을 드러낸다 — 문서가 단정적으로 쓰였지만 실제로는 안 정해진 것.
각 미결에 **담당 후보 / 결정 기한 후보 / 이게 안 정해지면 막히는 것**을 붙인다.
붙일 수 없으면 그것 자체가 더 큰 미결이다.

### 5. 지표 감사
"재밌게"·"쾌적하게" 같은 형용사 목표는 지표가 아니다. 각 지표가 **측정 가능한가**를 본다:
무엇을 / 몇 판 돌려 / 어떤 값이 나오면 통과인가. 셋 중 하나라도 없으면 미달.

### 6. 판정
표로 낸다:

```
| 항목 | 상태 | 근거/위치 |
|---|---|---|
| 필수 섹션 누락 | 2건 | 리스크, 마일스톤 |
| 근거 없는 수치 | 5건 | balance.md L12,L18,... |
| 공란 수치 | 1건 | 보스 HP |
| 명시 안 된 미결 | 3건 | ... |
| 성공 지표 정의 | 미달 | 승률 구간만 있고 측정 방법 없음 |
```

그리고 **게이트 판정 한 줄**:
- **통과** — 근거 없는 수치 0 · 미결 전부 명시 · 핵심 수치 공란 0 · 성공 지표가 숫자로 정의됨
- **반려** — 위 중 하나라도 미달. 무엇을 채워야 통과인지 목록으로.

경제 문서면 여기에 4항목을 더한다: F2P 완주 가능성 · 다크패턴 없음 · 확률 공개 등 컴플라이언스 ·
소스/싱크 수지가 표로 닫히는가.

## 역할 경계 — 섹션 표준 검사와 다르다

이 스킬은 **장르 무관 게이트**다: 수치에 근거가 있나, 미결이 드러나 있나, 성공 지표가 숫자인가.
**어떤 섹션이 있어야 하는가**는 게임마다 다르므로 여기서 정하지 않는다 — 그건 프로젝트
`CLAUDE.md`나 팀 섹션 표준 스킬(예: `gdd-16section-checker`) 소관이다.

| 검사 | 보는 것 |
|---|---|
| **이 스킬** | 근거 등급 · 미결 명시 · 지표 정의 (게이트 통과/반려) |
| 팀 섹션 표준 스킬 | 팀이 정한 섹션 구조가 다 채워졌나 (장르 특화 항목 포함) |
| gdd-pipeline MCP `review_doc_quality` | .md 파일의 빈 표·placeholder 기계 점검 |

셋은 겹치지 않는다. 둘 이상 쓸 수 있으면 같이 돌리고, 결과를 하나의 판정표로 합쳐 보고한다.

## 연동 (있을 때만)

**기획서가 사내 위키에 있는 경우** — Dooray MCP가 붙어 있으면 `dooray_wiki_list_pages` /
`dooray_wiki_get_page`로 정본을 직접 읽는다. 로컬 파일과 위키 내용이 다르면 **어느 쪽이 정본인지
먼저 확인한다** — 낡은 사본을 검수하면 게이트 자체가 무의미하다.

**기획 파이프라인 MCP(`gdd-pipeline` 등)가 붙어 있는 경우** — `measure_guardrails`로 자동 채점을
받아 이 스킬의 판정과 대조한다. 단, **자동 점수를 그대로 믿지 않는다.** 흔한 함정:

- 배열이어야 할 필드(`data_sources`, `kpi_list`)에 **줄글 문자열**이 들어가면 `len()`이 글자 수를
  세어 임계값을 자동으로 넘긴다 → "출처 3건 이상" 같은 가드레일이 **조용히 만점으로 통과**한다.
- 숫자여야 할 필드(`scenario_range` 등)에 `"±15%"` 같은 문자열이 들어가면 채점이 통째로 실패하거나
  프로젝트가 목록에서 사라진다.

따라서 자동 점수가 높게 나와도 **원본 필드의 타입과 실제 항목 수를 눈으로 확인**한 뒤 판정한다.
점수와 실물이 어긋나면 점수가 아니라 실물을 따른다.

응답에 `data_quality_warnings`가 있으면 그 항목의 개수는 줄글에서 **추정한 값**이다 — 그대로 인용하지
말고 원문을 세어 확인한다. 또 **종합 점수가 통과여도 개별 가드레일이 실패해 있을 수 있다**
(가중합이라 한두 개 실패를 다른 항목이 덮는다). `passed`가 `6/6`이 아니면 어느 항목이 왜 실패했는지
판정표에 그대로 옮긴다.

## 원칙
- **빈칸을 대신 채우지 않는다.** 그럴듯한 수치를 넣는 순간 게이트가 무력화된다.
- 사실·수치 보존. 검수 중 수치를 바꾸지 않는다.
- 문체는 건드리지 않는다(그건 polish-writing).
- "괜찮아 보임" 금지 — 통과/반려 둘 중 하나.

## 산출물
판정표 + 게이트 판정 한 줄 + "통과하려면 채워야 할 것" 목록.
반려면 game-designer(또는 meta-economy-designer) 단계로 되돌린다.
