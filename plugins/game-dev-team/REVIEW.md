# 리뷰: 스킬 트리거 정확도 & 에이전트 정의 품질

목표 렌즈: **다양한 게임을 만드는 범용 팀.** 특정 게임/장르/엔진에 종속되지 않아야 한다.

## A. 스킬 트리거 정확도
현재 스킬 description은 대체로 잘 분리돼 있으나, 아래를 점검·명시했다.
- `balance-sim`(전투 재미) ↔ `econ-sim`(경제) : "구분된다" 문구로 오발동 방지. OK.
- `polish`(연출) ↔ `artist`(정적 비주얼) : artist description에 연출 디렉션을 명시해 경계 정리.
- `concept-discovery`(0단계 발산) ↔ game-designer(1단계 수렴) : "정식 기획 이전" 명시. OK.
- `pr-review`(정확성) ↔ `balance-sim`(재미) : 둘 다 "리뷰/검증"이지만 대상이 다름(코드 vs 밸런스).

### 권장 검증 방법 (지속)
`skill-creator`로 각 스킬의 트리거 eval을 돌린다:
- 양성 예시(떠야 함) + 음성 예시(뜨면 안 됨)를 5~10개씩.
- 오발동·미발동을 세고 description을 조정. "무엇이 아닌지"(negative scope)를 넣을수록 정확해진다.

## B. 에이전트 정의 품질 (수정 반영)
| 에이전트 | model | 발견/조치 |
|---|---|---|
| pm | inherit | **Write 추가** — 트래커 MCP 없을 때 `docs/tasks/`에 태스크 문서 기록 |
| game-designer | inherit | **경계 명시** — core 담당, 경제는 meta-economy-designer 소관 |
| developer | inherit | **polish 스킬 추가** — 연출 구현(artist+developer 공동) |
| qa | inherit | 정확성 전담 명시 OK. 변경 없음 |
| artist | inherit | **description 정본 통일** — 연출(폴리싱) 디렉션 반영(드리프트 수정) |
| meta-economy-designer | inherit | core 통과 후 진입 명시 OK. 변경 없음 |

모델 배정: 역할 파일의 `model:`은 로더 호환성을 위해 전부 `inherit`. 실제 라우팅 기준은 `AGENTS.md`에서 관리 —
창작·판단 밀도 높은 작업(designer/dev/meta 성격)은 높은 추론 설정, 실행·검증형 작업(pm/qa/artist 성격)은 중간 추론 설정.
역할 경계: 재미(designer) / 정확성(qa) / 경제(meta) / 연출(polish=artist+dev) 4축이 겹치지 않게 분리 확인.

## B-2. 끊어진 참조 수정 (v0.8.0)
에이전트 frontmatter가 **존재하지 않는 스킬 4개**를 참조하고 있었다. 조용히 무시되기 때문에
"기획 게이트가 돌아가고 있다"고 착각하기 쉬웠던 결함이다.

| 에이전트 | 참조 | 조치 |
|---|---|---|
| game-designer, meta-economy-designer | `gdd-completeness-checker` | **스킬을 신규 작성**(게이트 판정 담당) |
| artist | `canvas-design`, `theme-factory` | 제거. artist는 Read/Write/Edit뿐이라 애초에 이미지 생성을 못 한다 → 책임을 "시안 스펙·톤 가이드 문서 산출"로 정정 |
| qa | `code-review` | 플러그인 내장 `pr-review`로 교체 |
| designer, meta | `polish-writing` | **스킬을 번들로 신규 작성**(문체 교정 담당, 수치는 불가침) |
| qa | (tools에 Write 없음) | 버그 리포트를 쓰라고 해놓고 쓸 수단이 없었음 → `Write` 추가(Edit은 제외, 코드 직접 수정 금지 유지) |

**교훈:** frontmatter의 `skills:`/`tools:`는 실패해도 조용하다. 릴리즈 전에 참조 ↔ 실체를
기계적으로 대조할 것.

## B-3. 훅으로 게이트 강제 (v0.8.0)
기존 규칙은 전부 산문이라 강제력이 없었다. 훅 4개를 추가해 실제 게이트로 만들었다.
설계 원칙 3가지:
1. **차단하지 않는다.** 최종 권위자는 사람이라는 이 플러그인의 전제와 훅의 강제 차단은 충돌한다.
   경고(`systemMessage`) + 모델 컨텍스트 주입(`additionalContext`)까지만.
2. **해당 없으면 즉시 조용히 종료.** 게임 프로젝트가 아니면 소음 0.
3. **어떤 예외도 exit 0으로 흡수.** 훅이 사용자 세션을 깨뜨리면 안 된다(`scripts/lib.mjs`의 `run()`).

밸런스 하드코딩 검사는 식별자를 토큰으로 쪼개 **정확 일치**로 판단한다(`costumeId`가 `cost`로
오인되지 않게). `frame_rate` 같은 비밸런스 `rate`는 단독 토큰을 인정하지 않아 걸러진다.

## B-4. 실사용에서 드러난 훅 결함 (v0.8.0, Farmtorio 작업 중 발견)

플러그인 레포에서 세션을 열고 **다른** 게임 프로젝트(`C:/00.SVN/Factory`)를 작업했더니,
`SubagentStop` 훅의 감사 로그와 에이전트 메모리가 **작업 대상이 아니라 이 레포에** 쌓였다.
`CLAUDE_PROJECT_DIR`이 세션을 연 디렉터리(=플러그인 루트)를 가리키기 때문이다.

이 레포는 공개이고 `.gitignore`도 없었다. `git add -A` 한 번으로 남의 게임 기획·확정 수치가
공개 저장소로 나갈 수 있었다. polish-writing 사내 문체 유출과 **같은 유형의 경로**다.

조치:
1. `.gitignore` 추가 — `.claude/agent-memory/`, `docs/pipeline/audit.log`, `state.json`, `*.bak*`
2. `lib.mjs`에 `isOwnRepo()` 추가 — 프로젝트 디렉터리가 `CLAUDE_PLUGIN_ROOT` 안이면
   `log-agent-gate.mjs`가 아무것도 쓰지 않는다. 자기 레포에 남길 이유가 없다.
3. 이미 쌓인 감사 로그는 실제 작업 대상 프로젝트로 이관.

**교훈:** 훅이 파일을 쓰는 경로는 "세션을 연 곳"이지 "작업 중인 곳"이 아니다.
플러그인이 자기 레포를 오염시킬 수 있다는 걸 전제로 가드를 먼저 넣어야 한다.
`.html`을 밸런스 훅 대상에 추가한 것도 같은 실사용 발견이다(단일 파일 웹 게임은 로직이 `<script>` 안에 있다).

## B-5. 실행형 에이전트의 `maxTurns`가 전반적으로 부족했다 (실사용 확인)

**developer 40 → 80, qa 25 → 50으로 상향.** qa는 검증을 다 돌리고도 **리포트를 쓰기 전에** 끊겼다 —
산출물이 0인 채로 턴만 소모한 최악의 형태다. 아래는 developer 사례 상세.


Farmtorio 작업에서 developer가 **3회 연속** 턴 한도를 소진했다. 소모 툴 호출은 51 / 40 / 47회였고,
**태스크를 S/M 단위로 잘게 쪼갠 뒤에도 재발**했다. 즉 태스크 크기 문제가 아니다.

구현 에이전트는 "고치고 → 돌려보고 → 안 맞으면 다시 고치는" 왕복이 길다.
그리고 **DoD에 실행 증거를 요구할수록 왕복이 더 늘어난다** — 품질 요구와 턴 예산이 상충한다.

1회차에는 소스가 **로드 불가 상태로 남았다.** 대상 프로젝트에 버전관리가 없어 데이터 손실 직전까지 갔다.

조치:
1. `maxTurns` 40 → **80**.
2. 대상 프로젝트 규칙에 **"코어를 고쳤으면 sync/빌드까지 한 사이클을 반드시 닫는다"**를 공통 DoD로 박았다.
   턴이 끊겨도 산출물이 로드 가능한 상태로 남게 하는 게 핵심이다.

**교훈:** 턴 한도는 "에이전트가 게을러지지 않게" 하는 장치가 아니라 **작업이 중간에 잘리는 지점**이다.
버전관리가 없는 대상에서는 그 지점이 곧 손실 지점이 된다. 한도를 정할 때 그걸 전제해야 한다.

## B-6. 에이전트 메모리가 프로젝트 상태를 중복 보관하고 있었다

Farmtorio 작업 중 실측했다. 에이전트 4명이 **같은 프로젝트 상태를 각자 자기 메모리에 따로** 쓰고 있었다:

```
designer/  project_farmtorio_stage1.md    4,159 bytes
pm/        project_farmtorio_pipeline.md  3,771
qa/        project_farmtorio.md           3,418
developer/ factory_farmtorio_sim.md       1,397
pm/        reference_farmtorio_docs.md    1,274

"§14가 정본" 같은 같은 사실이 → 6개 파일에 흩어짐
```

**왜 나쁜가.** 그 세션에서 지표 정본이 `§5 → §12-6 → §13 → §14`로 **세 번 이동**했다.
에이전트 메모리는 그 이동을 따라잡지 못한다. 다음 세션에 낡은 절을 정본으로 믿고 측정하면 판정이 틀린다.
그리고 메모리는 **에이전트별로 격리**돼 있어 서로의 낡은 사본을 교정해줄 수도 없다.

부수적으로 이건 **대상 프로젝트 지식이 플러그인 레포에 쌓이는** 구조적 오류이기도 하다(B-4 참조).

조치:
1. `agents/*.md` 6개 전부에 **메모리 규칙** 절 추가 — 프로젝트 상태는 `docs/pipeline/state.json`·
   프로젝트 `CLAUDE.md`가 정본이고 **매번 읽는다**. 메모리엔 **일하는 방식**(`type: feedback`)만 남긴다.
   "상태를 기억해야 할 것 같으면 그건 state.json에 빠졌다는 신호"라는 판단 기준도 넣었다.
2. 중복 상태 메모리 5건을 `_removed_<날짜>/`로 이관하고 `MEMORY.md` 인덱스의 죽은 링크 정리.
   남은 것은 전부 `feedback`(예: "코어 수정 직후 sync를 닫아라", "실측이 가정을 이긴다") — 이게 메모리의 본래 용도다.
3. 이관 전에 **대상 프로젝트 정본에 빠진 사실이 없는지 대조**했다. 하나 빠져 있었다
   (`sim/core.js`가 코어 정본이고 sync로 주입한다는 규율 — 로드 불가 사고를 두 번 낸 그 규칙).
   프로젝트 `CLAUDE.md`에 먼저 올린 뒤 정리했다.

**교훈:** 에이전트 메모리는 **변하지 않는 것**(일하는 방식)에만 쓴다.
변하는 것(상태·수치·정본 위치)은 레포에 두고 매번 읽게 해야 한다. 상태를 캐시하면 조용히 낡는다.

## B-7. 아트 트랙이 코드로만 존재하고 통제 장치에 배선되지 않았다 (v0.19.0, 전수 조사)

v0.12~v0.18 동안 리뷰 기록 없이 아트 트랙 2,848줄이 들어왔다. 전수 조사에서 나온 패턴은 하나다 —
**새 코드는 잘 작동하는데 플러그인 자신의 통제 장치(문서·게이트·에이전트 권한·CI)에 닿아 있지 않았다.**

### 1) `skills:` 를 권한으로 오해했다 (가장 컸다)
공식 문서 확인: `skills:` 는 **시작 시 전문 주입**이고, 목록 밖 스킬을 런타임에 부르려면
`tools:` 에 `Skill` 이 있어야 한다. 역할 6개 전원 `Skill` 이 없었으므로 **선주입 목록 = 접근 권한 전부**였다.
- 라우팅표가 공동 소유로 적은 **7건이 호출 불가**였다: developer×5(sprite-pipeline·ui-art-system·
  char-art-system·asset-3d-pipeline·asset-budget) · qa×1(visual-qa) · pm×1(release-notes).
  pm 은 `skills:` 자체가 비어 있어 소유 스킬 둘 다 못 썼다.
- 반대로 artist 는 아트 스킬 10개를 전부 적어 **매 호출마다 799줄**을 작업과 무관하게 주입받았다.
- 조치: 전원 `tools:` 에 `Skill` 추가 + 선주입을 "항상 쓰는 것"으로 축소. **팀 전체 1,958줄 → 324줄**
  (artist 799 → 126). pm 에는 `Bash` 도 줬다 — `release-notes` 가 트래커 MCP 없이는 `git log` 밖에 없다.

### 2) 작동하는 도구 1,003줄이 어느 문서에도 없었다
`art-direction` 의 스크립트 4개(ref-analyze·ref-classify·style-score·contact-sheet, 853줄)와
`ui-art-system` 의 `ui-kit-gen.mjs`(150줄), 그리고 `references/starter-kit/` 4개 파일이 SKILL.md 언급 **0건**.
에이전트는 SKILL.md 만 읽으므로 **없는 것과 같았다.** 실제로 돌려보니 둘 다 정상 동작했다
(ui-kit-gen → PNG 8장 + 9-slice manifest / fx-gen → 41파일). 코드 문제가 아니라 순수 문서 갭이었다.
- `char-art-system` 은 이미 `comfy-run --style profile.json` 을 쓰고 있었는데, 그 `profile.json` 의
  **생산자(`ref-analyze`)가 문서에 없어** 입력이 끊긴 상태였다.
- `sprite-pipeline` 은 정규화·알파정리·아틀라스를 산문으로 설명하는데, 그걸 실제로 하는 도구
  (`sprite-normalize`·`cutout`·`atlas-pack`·`sheet-split`)는 `char-art-system` 에 있고 연결이 없었다.
- 조치: 체인(분류→검수→측정→생성→채점)을 명령줄까지 문서화하고 스킬 간 링크를 걸었다.

### 3) `/gate` 가 아트(⑦)와 R 트랙을 판정할 수 없었다
`commands/gate.md` 의 게이트 표에 아트·visual-qa·asset-budget·R 언급이 **0건**이었다.
ORCHESTRATION §3·§9 엔 정의돼 있는데 판정 커맨드에 행이 없어, 22개 스킬 중 10개가 체크포인트 밖이었다.
- 조치: ⑦ 아트 행 + R0/R2/R5/R6/R7 표를 추가. "7은 가독성·예산, R7은 배포 가능성"으로 축을 분리해 명시.

### 4) CI 가 새 코드를 안 봤다
CI 는 `scripts/*.mjs`(1,010줄)만 `node --check` 했고 `skills/*/scripts/*.mjs` **17파일 2,848줄은
문법 검사조차 없었다.** 지금은 깨진 게 없었지만 CI 가 지켜주는 상태가 아니었다.
- 조치: 문법 검사를 26파일 전체로 확장. **생성 도구 스모크**(starter 스펙 → 실제 PNG/manifest) 추가 —
  이걸로 2)번이 조용히 재발하지 못한다. 잘못 부를 때 스택트레이스를 내는지도 검사한다.
- 그 검사에서 스크립트 **10개가 `--help` 를 경로로 오해해 스택트레이스를 뱉는 것**을 발견해 인자 검증에
  플래그 거부를 넣었다.

### 5) pre-commit 이 비Windows 에서 모든 커밋을 막았다
`powershell.exe` 를 무가드로 호출하고 `$? -ne 0` 이면 exit 1 — 없는 환경에선 127 이라 **전면 차단**이었다.
바로 아래 node 는 `command -v` 로 가드돼 있었고, `validate-plugin.mjs` §8 이 같은 드리프트 검사를
이미 Node 로 한다(그 주석에 "PowerShell 없는 CI에서도"라고 적혀 있다).
- 조치: 양쪽 다 가드. 단, 둘 다 없으면 조용히 통과시키지 않고 명시적으로 막는다.

### 6) 재발 방지를 검사로 옮겼다
문서에 규칙을 적는 것만으로는 같은 사고가 반복된다(B-2 의 교훈). `validate-plugin.mjs` 에 두 검사를 넣었다:
- **§7b** 스킬의 `scripts/*` 가 그 스킬 문서에 언급되는가 → 없으면 오류.
- **§7c** 라우팅표가 소유자로 지목한 스킬이 그 에이전트에서 **실제로 도달 가능**한가
  (선주입에 있거나 `tools:` 에 `Skill` 이 있어야) → 아니면 오류.
- 선행 조건으로 `KNOWN_TOOLS` 를 공식 목록으로 교체했다. `Skill` 이 빠져 있어서 **정당한 수정에
  경고가 떴고 그게 수정을 막고 있었다** — 검사기가 틀리면 검사기를 먼저 고쳐야 한다.

### 7) 함께 정리한 것
- `INSTALL.md` 가 미러에 복사되지 않았다(CANON_FILES 누락) → Codex 로컬 설치본에 원클릭 설치 문서가 없었다.

  **두 세대가 화해되지 않은 상태**였고, 문서 없는 스크립트가 정확히 그 이음선에 있었다 → 전부 한글화.
  (`visual-qa` 는 §5 증거 규칙을 이미 갖고 있었다 — 본문 언어만 문제였다)
- 트리거 충돌 1건("스프라이트 만들어줘" → char-art-system + sprite-pipeline) → 후자로 정리.

  후보는 Windows 에서만, POSIX 후보 추가. 설치 문서에 **플랫폼 전제를 명시**했다(CUDA 없으면 미달이

**교훈:** 기능을 붙일 때 코드만 붙이면 절반이다. **문서(에이전트가 읽는 곳) · 게이트(판정하는 곳) ·
권한(호출 가능한지) · CI(지켜주는 곳)** 네 군데에 같이 배선해야 그 기능이 실제로 존재한다.

## B-10. polish 에 도구가 0이었다 — 그리고 거기 안전 문제가 숨어 있었다 (v0.25.0)

아트 축 점검에서 `polish` 가 **37줄 산문에 도구 0** 인 게 남은 가장 큰 갭이었다.
연출은 체감 품질의 큰 비중인데, "타격감 넣어줘"에 사람마다 다른 결과가 나오는 상태였다.

### 예상 밖의 발견: 안전 게이트가 없었다
조사에서 나온 것 — **광과민성 발작 위험이 이 플러그인 어디에도 판정되지 않고 있었다.**
WCAG 2.3.1(Three Flashes or Below Threshold)은 1초 안 3회 초과 플래시를 금지하고,
콘솔 플랫폼 심의도 같은 종류를 본다. 이건 "느낌이 아쉽다"가 아니라 **사람을 해칠 수 있고
출하가 막히는** 축이다. 지금까지 게이트 전부가 품질 축이었고 **안전 축은 처음이다.**

`flash-check.mjs`: 상대휘도 대립 변화 >= 0.10 + 어두운 쪽 < 0.80 을 플래시로 세고,
1초 슬라이딩 창에서 3회 초과면 미달. 루프가 1초보다 짧으면 반복으로 실효율이 올라가는 것도 반영.
`fx-art-system` manifest 에 frames·fps·loop·blend 가 있어 기존 산출물이 바로 검사된다.
가산 합성이라 배경 위에 얹은 결과로 재고, 기본 배경을 어둡게 둔다(대비 최악 조건).

**판정 기준을 두 번 고쳤다.** 1차 구현은 프레임 **평균** 휘도로 판정해서, 면적 5% 짜리
28회/초 스트로브가 평균 변화 0.05(임계 0.10 미달)로 **"충족"으로 나왔다.** 그건 틀린 답이다 —
WCAG 는 면적을 별도 면제 조항(시야 10도 안 25% 이하)으로 다룬다. 그래서
(1) 어느 영역이든 임계를 넘게 깜빡이면 플래시로 세고 (2) 면적은 면제 판단용으로 따로 보고하고
(3) 초과했지만 면적이 작으면 `조건부` 로 내 **화면 크기를 아는 사람에게 넘긴다** 로 바꿨다.

### feel-audit — "느낌"과 "틀린 것"을 분리했다
연출은 주관 축이라 기계가 판정할 수 없다고 넘기기 쉽지만, **느낌과 무관하게 틀린 것**이 섞여 있다.
- **미달**(취향 무관): 무게역전(강한 쪽이 더 약함) · 예산초과(피드백이 액션 간격을 넘어 다음
  입력이 묻힘) · 접근성(모션 감소 경로 없음 — polish 가 이미 P2 에서 요구하던 것을 검사로 만들었다)
- **경고**(관행 이탈): hit-stop·흔들림 범위, 이징 방향·일관성, 반응 지연, 사운드 누락.
  **게이트를 막지 않는다** — 턴제면 hit-stop 상한이 무의미하고 리듬 게임이면 반응 기준이 더 엄격하다.

연출 상수를 `feel.json` 한 곳에 모으게 했다(뼈대 동봉). 코드에 숫자를 따로 박으면 이 감사는 장식이다.

### 이번에도 동봉 기준값이 자기 검사에서 떨어졌다
팔레트 때(B-8)와 같은 일이 반복됐다 — 내가 만든 starter `feel.json` 이 **미달 4건**이었다.
- 예산초과 3건: 액션 간격 400ms 로 잡았는데 강타·크리 피드백이 그 60%를 넘었다.
  400ms 는 비현실적으로 빠른 값이었다 -> 700ms 로 고쳤다.
- 무게역전 1건: **이건 도구의 오탐이었다.** "플레이어 피격"(무게 4)과 "적에게 강타"(무게 3)를
  한 축에서 비교한 것이다. 서로 다른 이벤트 부류인데 무게를 견주는 게 틀렸다.
  -> `class` 필드를 도입해 **같은 부류 안에서만** 비교하고, 항목이 1개인 부류는 [공백]에 고지한다.
  **게이트에서 오탐은 없는 것보다 나쁘다** — 한 번 틀리면 아무도 안 믿게 된다.

### CI 에서 또 허위 통과를 잡았다
스트로브 픽스처 생성이 `file://$repo` 형태라 Windows 에서 깨졌는데, `flash-check` 가
manifest 없음으로 비정상 종료해서 **"스트로브 적출 O" 로 보였다.** 안전 검사가 실제로는
안 돌았는데 통과로 읽힌 것이다. 미리 넣어둔 픽스처 개수 가드(`-eq 16`)가 그걸 잡았다.
`pathToFileURL` 로 고치고 재검증했다(16개 생성 -> 28회/초 적출 확인).
**절대 안 뜨는 안전 검사는 없는 것보다 나쁘다** — 있다고 믿게 만든다. 그래서 CI 는
"동봉 값이 통과하나"와 "위험을 실제로 잡나"를 **양방향으로** 본다.

### 배선
`art-gate` 에 두 축을 편입해 아트 통합 판정이 **5축**(CVD·오버플로·예산·연출·플래시)이 됐다.
검사기 GATE_TOOLS 에 추가했고 — **또 AGENTS.md 가 모른다고 잡혔다**(§7b-2 가 세 번째로 값을 했다).

**교훈:** 주관 축이라고 판정을 포기하면 그 안에 섞인 **안전 문제와 논리 모순**까지 놓친다.
"느낌이 좋은가"는 사람이 하고, "느낌과 무관하게 틀린 것"은 기계가 한다 — 그 선을 긋는 게
일이었다. 그리고 안전 축은 품질 축과 다르게 다뤄야 한다: 미달이 "아쉽다"가 아니라 "막힌다"다.

**남은 것**: `sprite-pipeline`·`asset-3d-pipeline` 은 여전히 도구 0이다(3D 는 Blender MCP 전제라
우선순위가 낮다). 그리고 v0.19~v0.25 전부가 조사 기반이고 **실사용 검증은 아직 0**이다.
## B-11. sprite-pipeline 은 "만드는 도구"만 있었다 (v0.26.0)

앞서 이 스킬을 "도구 0"이라고 적었는데 **부정확했다.** v0.19 에서 `char-art-system` 의
`sheet-split`·`sprite-normalize`·`cutout`·`atlas-pack` 으로 배선해뒀다. 정확한 진단은
**만드는 도구는 있고 판정하는 도구가 없었다**는 것이다 — 다른 아트 축은 전부 판정 도구를
받았는데(cvd-check·pseudo-loc·asset-baseline·flash-check·feel-audit) 여기만 빠졌다.

`sprite-normalize` 는 규격을 통일하고 `atlas-pack` 은 점유율을 출력하지만 둘 다 **"이게
괜찮은가"를 말하지 않는다.** SKILL.md 의 QA 체크리스트 5줄이 산문으로만 있었고, 그중 4개가
기계 판정 가능했다(타이밍은 `polish` 소관).

### sprite-qa.mjs
- **미달**: 캔버스 크기 섞임 · **정체성 드리프트**(프레임 간 Lab 히스토그램 유사도 —
  이 스킬이 스스로 1번 위험으로 적어둔 것) · 아틀라스 점유율
- **경고**: 떨림 · baseline 산포 · 알파 품질(고아 섬·구멍·프린지) · 축소 판독성

### 떨림 판정을 세 번 고쳤다 — 오탐이 게이트를 죽인다
1차: **절대 px 로 2차 차분**을 봤다. 진폭 3px 짜리 정상 걷기 사이클이 2차 차분 1.91px 를
내서 **오탐**이 났다 — 부드러운 사인 운동도 가속이 0이 아니다.
2차: **중위값 대비 이상치 배수**로 바꿨다. 정상은 통과했지만, 결함이 2개 이상이면 중위값이
올라가 서로를 가려 결함 시퀀스를 **놓쳤다**(배수 2.19 로 임계 2.5 미달).
3차: **둘을 같이 본다.** (1) 스프라이트 최소변 대비 비율 — 스케일 무관하게 "얼마나 격렬한가"
(48px 스프라이트에서 17.7px = 37% 는 격렬, 1.9px = 4% 는 부드러움). (2) 중위 대비 이상치 배수 —
전체는 부드러운데 한 프레임만 튀는 경우.
픽스처 3종으로 검증했다: 정상 걷기(충족·경고 0) / 부드러움+단일 스파이크(경고) / 다중 결함(미달).

### 고아 섬을 미달에서 경고로 내렸다
처음엔 미달로 잡았는데 **떨어진 덩어리가 의도적일 수 있다** — 던진 무기, 떠 있는 장식,
잔상 이펙트. 미달로 두면 그런 스프라이트가 전부 반려된다.
임계도 너무 타이트해서(0.004) 심어둔 9px 점을 못 잡았다 -> 0.05 로 올리고 경고로 내렸다.

**교훈:** "도구가 없다"와 "판정 도구가 없다"는 다른 진단이고, 후자가 정확했다.
생성 도구만 있으면 산출물이 나오지만 그게 쓸 만한지는 아무도 모른다.
그리고 **임계값은 반드시 정상 케이스로 오탐을 먼저 확인해야 한다** — 이번에 세 번 고쳤고,
세 번 다 "정상인데 걸린다"가 먼저였다. 그래서 CI 도 "정상 통과"를 결함 적출보다 먼저 검사한다.

`art-gate` 가 **6축**이 됐다(CVD·오버플로·예산·연출·플래시·스프라이트).
GATE_TOOLS 에 추가 — **또 AGENTS.md 가 모른다고 잡혔다**(§7b-2 네 번째 적발).

**남은 것**: `asset-3d-pipeline` 만 판정 도구가 없다(Blender MCP 전제라 우선순위 낮음).
그리고 v0.19~v0.26 전부가 조사 기반이고 **실사용 검증은 여전히 0**이다.
## B-12. 첫 실사용 검증 — hex-danmaku 에 아트 게이트를 걸었다 (v0.27.0)

v0.19~v0.26 전부가 조사 기반이고 실사용 검증이 0이었다. 실제 프로젝트
(hex/hex-danmaku · 턴제 헥사 탄막 · PNG 90장)에 처음 걸었다.

### 마찰 1 — 도구가 가정한 입력 형식이 프로젝트와 달랐다
`cvd-check` 는 `palette.json` 을 가정하는데 이 프로젝트는 색이 **`art-data.js` 의 JS 컬러맵
23개 + `styles.css` 변수**에 있다. 어댑터를 만들어야 돌아갔다(약 80줄).
그리고 변칙탄은 색이 아니라 **CSS `filter: hue-rotate()`** 로 파생되므로, 실제 색을 알려면
SVG feColorMatrix 행렬을 계산해야 했다(hue-rotate 는 HSL 회전이 아니다).

**교훈**: 판정 도구는 입력 형식을 하나로 가정하면 실제 프로젝트에서 어댑터 없이는 안 돈다.
다만 어댑터가 프로젝트 쪽 코드라는 건 맞다 — 플러그인이 모든 프로젝트 구조를 알 수는 없다.
대신 **어댑터를 쓰라는 안내가 문서에 없었다.**

### 마찰 2 — 어댑터가 값을 잘못 매핑해 없는 문제를 만들었다
`bossFire 0.45s`·`heroDead 0.55s` 를 화면 흔들림으로 매핑했는데, 실제로는 엔티티
scale/opacity 애니메이션이었다(화면 흔들림은 `board-shake 0.32s ±4px` 하나뿐).
그래서 "흔들림 450/550ms > 권장 400ms" 경고 2건이 **허위**로 났다.

**교훈**: 어댑터는 판정 결과의 신뢰도를 결정한다. 매핑을 확인하지 않으면 도구가 정확해도
틀린 답이 나온다. 실사용 리포트에는 **어댑터가 무엇을 어떻게 매핑했는지** 같이 적어야 한다.

### 도구 결함 1 — 유병률 가중이 없었다 (고쳤다)
`cvd-check` 가 붕괴 7건을 **평면 목록**으로 냈는데, 그중 5건이 전색맹(유병률 <0.01%) 전용이었다.
흔한 유형(녹색맹 남성 약 6%)의 진짜 2건이 그 안에 묻혔다.
-> 심각도 3단계로 갈랐다: **정상 시야에서도 붕괴**(모든 플레이어 문제) >
**흔한 색약(적/녹, 남성 약 8%)** > **드문 유형만**(청색맹·전색맹, <0.01% -> `조건부`, 출하 안 막음).
같은 데이터가 "붕괴 7개"에서 "치명 1 · 우선 1 · 낮음 5"로 바뀌었다.

**이게 실사용으로만 나올 수 있는 결함이었다.** 합성 팔레트로는 쌍이 적어서 묻히는 현상이 안 보인다.

### 도구 결함 2 — turnBasedGame 필드가 장식이었다 (고쳤다)
`feel.json` 스키마에 `pace.turnBasedGame` 을 넣어뒀는데 도구가 읽지 않았다. 턴제 게임에서
리포트가 "**액션 간격 미설정**"을 냈고, 그건 누락처럼 읽힌다 — 실제로는 **해당 없음**이다
(다음 액션이 플레이어 입력을 기다리므로 피드백이 입력을 가릴 수 없다).
-> 예산 검사를 명시적으로 건너뛰고 [공백]에 "누락이 아니라 해당 없음"으로 적는다.

### 게임 쪽 실제 발견 (도구가 잡은 것)
1. **`mine.X` vs `coin.X` 가 정상 시야에서 dE 0.0** — 지뢰(즉사)와 코인(픽업)이 본체색
   (`#fbbf24`)·하이라이트(`#fde68a`)·음영(`#d97706`)이 **완전히 동일**하다. 구분이 형태(도화선)와
   외곽선(`#451a03` vs `#7c4a03`)에만 의존한다. 렌더 크기 약 21~24px 에서 이동 중에 충분한지는
   `visual-qa` 의 사람 검수 몫이다. **색각이상 문제가 아니라 모든 플레이어의 문제다.**
2. **`warnStroke`(`#f87171`) 가 탄(`#fb7185`) 과 거의 같은 색** — 정상 시야 dE 10.5(임계 10 턱걸이),
   **녹색맹 9.8(붕괴)**, 청색맹 3.1. 위험 예고가 예고 대상과 같은 색이면 예고가 안 된다.
3. **사운드가 전혀 없다**(Audio·mp3/wav/ogg 전무). 타격 피드백이 시각만이다.
4. **코드 주석이 틀렸다** — `/* 변칙탄 텔레그래프: zig=보라, slow=하늘 */` 인데 CSS filter 를
   실제 계산하면 zig=올리브황(`#bba700`), slow=보라(`#b379ff`) 로 **반대**다.
5. `poses/` 4개 PNG 가 커밋 안 된 채 남아 있다(2026-08-22) — `pose-skeleton.mjs` 를 인자 없이
   돌린 잔여물이다. v0.19 에서 CI 를 임시 디렉터리로 옮겨 이 부류를 막았지만 **이미 생긴 건 남는다.**

### 적용 안 된 도구 (정직하게)
- `sprite-qa`: `assets/extracted/1x` 는 엔티티별 단일 PNG(16~24px)라 **애니메이션 시퀀스가 아니다.**
  프레임 정합 개념이 성립하지 않는다 — 해당 없음.
- `flash-check`: 이 게임의 명멸은 **CSS 애니메이션**(`blink 0.7s steps(2) infinite` 등)이고
  PNG 프레임이 아니다. 도구가 CSS 를 못 읽는다 → **측정 불가.** 수동 계산으로는 1.1~1.4회/초라
  WCAG 3회/초 상한 아래지만, **도구로 판정하지 못했다는 게 사실이다.**
- `pseudo-loc`: UI 문자열이 6개 파일에 흩어져 있어 슬롯 매핑을 만들 수 없었다 — 측정 불가.
- `asset-budget`: Unity `.meta` 를 읽는 도구다. 웹 프로젝트에는 적용되지 않는다.

**교훈:** 실사용 한 번에 **도구 결함 2개 + 어댑터 함정 1개 + 적용 불가 4건**이 나왔다.
합성 픽스처로는 안 나오는 것들이다. 특히 유병률 가중은 "쌍이 많아질 때만" 드러나는 결함이었다.
그리고 **적용 불가 4건이 절반**이다 — 도구가 가정하는 입력(팔레트 JSON·PNG 시퀀스·Unity meta)이
실제 프로젝트 구조와 다를 때가 흔하다는 뜻이다. 그걸 "측정 불가"로 정직하게 내는 게 맞고,
지금 도구들은 그렇게 한다.
## C. 드리프트 방지 (프로세스 교훈)
GitHub push를 손수 작성한 내용으로 하다 소스와 어긋난 사례가 있었다.
→ **항상 소스(플러그인 디렉터리)를 정본으로 두고, 그 내용을 그대로 push**한다. 손으로 다른 내용을 push하지 않는다.
