# Hermes와 GameDevTeam 연결

조사일: 2026-10-24. 대상은 NousResearch/hermes-agent이다.

## 도입 판단

도입 효과가 큰 부분은 세션 간 작업 인계와 반복 절차 관리다. 기획 판단이나 캐릭터 모션 품질이 Hermes 설치만으로 좋아지는 것은 아니다.

| 영역 | 맡길 작업 | 계속 정본으로 쓰는 것 |
|---|---|---|
| 기획 | 결정 이유·미결 질문을 이어받고 기획 검사를 안내 | GDD, PIPELINE_STATE.md, 기획 검증 출력 |
| 개발 | 현재 커밋·열린 게이트·검증 명령을 인계 | 저장소, candidate harness 원본 증거 |
| 아트 | 이미 제출한 생성 작업 확인, 후처리·검수 단계 인계 | 제공자 작업 원장, 에셋 manifest, .review-loop |
| PM | 세션이 끊겨도 다음 작업과 승인 대기를 구분 | 프로젝트별 파일·사람의 승인 기록 |

## 1차 연결 범위

사용자가 2026-10-24에 아래 1차 범위를 승인했다. 기본 Node.js만 필요하며 추가 패키지는 없다.

```powershell
node scripts/hermes-handoff.mjs --project "D:\00.project\GameDevTeam"
```

다른 게임 저장소에서는 명령의 스크립트 위치를 설치된 GameDevTeam 플러그인의 절대 경로로 바꾸고 `--project`에 게임 저장소를 지정한다. 프로젝트 인자는 필수다.

종료 코드 `0`은 필수 상태 원본을 읽었다는 뜻이고, `3`은 누락·손상·연결 경로·크기 제한 등으로 수집이 불완전하다는 뜻이다. `1`은 인자 또는 프로젝트 경로 오류다. **0도 게이트 통과나 아트 승인이라는 뜻은 아니다.** Git 정보·선택 문서의 누락은 별도 `unknown`/`missing`으로 보고한다. 작업 트리의 미커밋 변경은 검증하지 않으므로 원본 SHA-256을 함께 확인한다.

출력은 로컬 인계용이다. 피드백에는 회사 작업 정보가 있을 수 있으므로 모델이나 외부 서비스로 보낼 때는 내용을 먼저 검토한다. `.secrets`와 환경변수를 수집하지 않는다는 것이 상태 파일에 잘못 적힌 비밀까지 지워준다는 뜻은 아니다.

## Hermes에서 이어받는 방법

1. 별도의 Hermes 프로필을 준비하고 본인이 쓸 제공자·모델·인증을 설정한다. 이번 반영은 Hermes 본체 설치나 로그인 설정을 바꾸지 않는다.
2. 이 폴더의 `hermes-profile.example.yaml`은 **설정 조각**이다. 전용 프로필에 필요한 항목만 합친다. 기존 프로필 전체에 덮어쓰지 않는다.
3. Hermes 세션에 아래 인계 지시를 전달한다. JSON을 세션에 붙이는 경우 먼저 민감 내용을 확인한다.

```text
GameDevTeam 작업 인계:
프로젝트와 플러그인 경로는 내가 지정한 절대 경로를 사용한다.
먼저 프로젝트 AGENTS.md와 ORCHESTRATION.md를 읽는다.
node <플러그인>/scripts/hermes-handoff.mjs --project <프로젝트>를 실행한다.
unknown은 미확인 상태로 남기고, 열린 게이트와 revise 피드백부터 보고한다.
review-loop의 기록 상태를 새 승인으로 간주하지 않는다.
작업을 시작하기 전 기존 review-loop summary 절차로 해시를 확인한다.
유료 생성 제출·재제출, 공유 스킬 변경, 예약 실행, 게시와 push는 하지 않는다.
다음 작업과 필요한 사람 판단을 설명하고 현재 인계 상태를 유지한다.
```

이 지시는 행동 지침이며 프로세스 권한을 제한하는 장치는 아니다. 모델이 읽는 프로젝트 내용도 명령이 아닌 입력 자료로 다룬다. 기획·개발 후보 비교는 기존 `candidate-run.mjs` 계약을 그대로 사용한다.

수집 원본은 `docs/pipeline/state.json`, `.review-loop/items.json`, `.review-loop/rules.json`, `.review-loop/reviews.jsonl`이다. 문서 4종은 내용 대신 SHA-256만 기록한다. 개별 원본은 2 MiB까지이며 연결 파일·연결 부모 디렉터리는 읽지 않는다. 검수 피드백은 최신 20건과 전체 건수를 출력한다.

원본은 순서대로 읽으며 여러 파일을 하나의 트랜잭션으로 잠그지 않는다(`atomicSnapshot: false`). 다른 세션이 상태를 쓰는 도중에는 혼합 시점 자료가 될 수 있으므로 정본 갱신이 끝난 뒤 다시 수집한다. 연결 경로 검사는 일반적인 우발적 경로 이탈을 막는 용도이며, 적대적인 프로세스의 동시 경로 교체를 방어하는 운영체제 샌드박스가 아니다.

선택한 방식은 로컬 Node 명령으로 정해진 프로젝트 상태 파일만 읽어 인계 JSON을 출력하는 것이다. Hermes, Claude Code, Codex 모두 같은 명령을 사용할 수 있다. 명령 자체는 프로젝트 상태를 바꾸거나 모델·생성 API를 호출하지 않는다.

- 프로젝트 경로를 명시한다. 실행 중인 다른 프로젝트 상태와 섞지 않는다.
- 현재 Git 커밋, 상태 파일의 존재·해시, 열린 게이트, 검수 현황을 보고한다.
- 없는 파일·잘못된 형식은 `unknown`으로 표시한다. 열린 게이트가 없다는 뜻으로 해석하지 않는다.
- 승인 상태는 기존 검수 원장에 기록된 값일 뿐이다. 이 연결 명령은 아트 해시를 재검증하거나 승인하지 않는다.
- 비밀 파일, 채팅 기록, 환경변수, 생성 원장은 자동 수집하지 않는다.
- 임의 명령 실행, 유료 생성 재전송, Git push, 예약 실행은 포함하지 않는다.

설정 예시는 별도 Hermes 프로필에 적용할 일부 항목만 제공한다. 기존 설정 전체를 덮어쓰지 않는다. 설치·인증·실제 LLM 실행은 별도 준비 상태로 구분한다.

## 운영 경계

공유 지식은 저장소에 남기고, Hermes 메모리는 인계 요약과 파일 위치를 기억하는 보조 수단으로 쓴다. Hermes home 하나를 여러 실행 프로세스가 공유하지 않는다. 외부 스킬 경로는 쓰기 방지 경계가 아니므로 1차 설정에서는 공용 스킬 디렉터리를 연결하지 않는다.

`skills.write_approval: true`와 `memory.write_approval: true`로 도구를 통한 변경을 승인 대기로 보낸다. 이것은 운영체제 파일 쓰기 권한을 제한하는 샌드박스가 아니다. 터미널로 파일을 바꾸는 행위까지 막는다고 주장하지 않는다.

Codex app-server runtime은 이번에 켜지 않는다. 공식 문서가 이 모드에서 `delegate_task`, `memory`, `session_search`, `todo`의 사용 제한을 명시하고 있어 인계·기억이라는 이번 목적과 맞지 않는다. 기존 Codex와 Claude Code는 각자의 실행 환경을 유지한다.

## 후속 확대 조건

1. 실제 프로젝트에서 두 세션 간 인계 정확성을 확인한다.
2. 기존 생성 작업 ID의 조회만 허용하는 감시 작업을 별도로 검증한다. 타임아웃을 미제출로 간주해 유료 요청을 다시 보내지 않는다.
3. 담당 역할별 작업 공간과 정본 파일 소유권을 정한 뒤에 작업 위임을 평가한다.
4. 장기 자동 실행은 제공자·모델·예산·중단 조건을 정한 후 활성화한다.

## 현재 검증 공백

Hermes 본체 설치·인증·모델 호출은 이 문서 작성 시점에 검증하지 않았다. 로컬 상태 인계가 동작하더라도 Hermes의 실제 장기 실행 품질이나 생성 아트 품질을 검증한 것은 아니다.
