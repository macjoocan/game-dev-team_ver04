# 데브팀 구조의 객관적 점검

점검일: 2026-10-25. 대상: v0.50.0 로컬 소스와 이 PC의 실행 결과. 원본 Hermes/Harness² 제품의 성능 평가가 아니다.

## 판단

**사람이 감독하는 게임 개발 보조 체계로는 유용하다. 무인 개발팀이나 게임 품질 개선 효과가 입증된 체계로 보기는 이르다.** 역할·상태·증거·승인 경계가 있고 결정론적 검증 도구를 재사용하는 점이 강점이다. 반면 실제 프로젝트의 제작 시간·재작업률·게임 품질 개선은 측정하지 않았다. 테스트 수를 그 효과의 증거로 대체하지 않는다.

## 코드와 실행 근거로 본 상태

| 영역 | 확인된 점 | 한계 |
|---|---|---|
| 작업 재개 | 동일 프로젝트 원장 재로딩, 이벤트·역할·다음 행동 유지 | 자동 일정 관리나 실제 에이전트 기동은 아님 |
| 동시 작업 | 배타 쓰기 잠금 + 읽었던 revision 확인 | 신원 인증이나 프로젝트 전체 파일 잠금은 아님 |
| 후보 비교 | 입력·평가·도구 해시 고정, 같은 조건 실행, 재개 검증 | 지표 자체가 재미/아트 품질을 대표하는지는 별도 판단 |
| 증거·승인 | 첨부 파일 최신성과 사람 승인을 구분 | 동일 해시는 테스트 통과나 검사 대상 최신성의 증명이 아님 |
| 경험 축적 | 제안과 승인 공통 규칙 분리 | 자동으로 경험을 검증·일반화하는 학습 엔진은 아님 |
| 플랫폼 | Windows에서 프로세스 종료 가능 환경의 테스트 통과 | 샌드박스와 OS 권한 차이, 링크 테스트 생략, 원격 Ubuntu CI는 별도 |
| 배포 | 공식 소스→미러 동기화·무결성 검사 | 설치 캐시는 별도 갱신·세션 재시작이 필요 |

## 이번에 확인하고 수정한 결함

1. **오래된 세션의 상태 덮어쓰기:** 잠금은 동시 쓰기만 막고 이전 판단의 후속 쓰기는 막지 못했다. 기존 원장 변경에 관측한 revision을 요구하도록 수정했다. 충돌 시 변경하지 않고 다시 읽게 한다.
2. **실험과 정본 경로 중첩:** 실제 작업 원장·승인 기록·공용 스킬을 후보 cwd로 사용할 수 있었다. 정본 경로 및 상위/하위 겹침을 계약 검사에서 거부한다.
3. **후보끼리 같은 폴더 사용:** 서로 다른 후보 ID가 같은 작업 폴더를 가리키는 계약이 통과했다. 후보 cwd끼리 동일/상하위 중첩도 거부한다.
4. **프로세스 종료 실패를 무시한 대기:** Windows taskkill의 실패 결과가 무시돼 실행이 오래 남을 수 있었다. 정리 실패 이유와 PID를 기록하고 직접 자식 종료를 시도하며, 다음 후보 실행과 해당 실행의 resume을 막는다. 잠금은 사람이 실제 정리를 확인할 때까지 남긴다. 잠금을 지우는 것만으로 blocked 실행을 resume할 수 없다.

각 결함은 실패하는 테스트를 먼저 확인한 뒤 수정했다. 정상 경로뿐 아니라 오래된 revision·잘못된 후보 경로·종료 거부·정리 차단 후 재개라는 음성 대조군을 포함했다.

## Windows 실패 원인 정정

이전 보고의 `null !== 3` 두 건을 Windows 자체 결함으로 단정하면 부정확하다. 테스트 전용 자식을 만든 최소 재현에서 제한 환경은 taskkill exit 1(접근 거부), 같은 재현은 샌드박스 밖에서 exit 0이었다. 기존 타임아웃 테스트 두 건도 종료 권한이 있는 환경에서는 수정 전부터 통과했다.

따라서 원래 실패의 직접 원인은 이 실행 환경의 프로세스 트리 종료 제한이다. 별도로 확인된 코드 결함은 종료 실패 결과를 무시한 대기와 복구 처리였으며 위와 같이 보강했다. 개발자 모드는 파일 링크 생성 권한과 관련 있고 에이전트 샌드박스의 프로세스 권한을 풀지 않는다. 설정 자체는 변경하지 않았다.

## 최종 검증 결과

프로세스 테스트가 만든 자식 트리를 정리할 수 있는 실행 환경에서 작업 트리 전체 테스트 **65건 중 64건 통과, 실패 0, 생략 1**. 생략은 파일 심볼릭 링크 생성 권한이며 통과로 세지 않았다. 별도의 종료 거부 테스트는 주입한 실패 결과로 해당 경로를 검증한다. 이 작업 트리 전체에는 별도 Higgsfield 테스트 8건이 포함돼 있다.

`node scripts/ci-local.mjs`를 Git Bash `bash -e`에서 실행한 결과 **19/19 단계 통과**. 이는 로컬 Windows 결과이며 GitHub Ubuntu 결과가 아니다. 무결성 검사와 소스/미러 일치도 확인했다.

원시 증거: [전체 테스트](../docs/verification/team-audit-2026-10-25/full-tests.txt), [로컬 CI](../docs/verification/team-audit-2026-10-25/local-ci.txt). 배포 미러에서는 증거 파일이 아닌 이 원본 저장소의 docs 경로를 확인한다.

## 아직 부족한 부분

- **실제 프로젝트의 효과 측정:** 같은 규모 작업에서 제작 시간·수정 횟수·사람 검수 통과율을 비교하지 않았다. 현재는 기능 정확성 근거이며 생산성 성과의 근거가 아니다.
- **역할 인계와 실제 실행의 차이:** Codex의 6개 역할은 메인 세션이 지키는 규칙이다. 로컬 task handoff가 자동으로 전문 에이전트를 기동하거나 파일 소유권을 강제하지 않는다.
- **게임 품질 평가:** 재미·모션 자연스러움·UI의 게임다운 완성도는 시뮬/규격 테스트만으로 확정하지 못한다. 기존 플레이테스트·실제 화면 검수·사람 승인 절차가 필요하다.
- **실행 격리:** 후보 경로 검사는 신뢰하는 검증 명령을 위한 계약 검사다. 악성 코드의 임의 쓰기를 막는 OS 샌드박스가 아니다. Windows 정상 종료 후 남긴 독립 백그라운드 프로세스의 완전한 정리는 미검증이다. 검증 명령은 전경에서 완료하도록 구성한다.
- **운영 자동화:** 유료 작업 감시·스케줄러·무인 자기수정·자동 게시·PC 간 원장 동기화는 구현하지 않았다. 이 기능들을 이미 있는 것처럼 운영하면 안 된다.
- **장기 세션 검증:** 실제 팀의 여러 세션·여러 PC에서 장기간 운영해 본 결과는 아직 없다. 잠금과 revision은 단위/통합 테스트로 확인한 범위다.

이 항목들은 이번 코드 수정을 더 붙이면 자동으로 해결되는 결함과 구분한다. 실제 작업 근거와 운영 조건이 필요한 검증 공백이며, 현재 기능의 완료·승인 판정을 부풀리는 용도로 사용하지 않는다.

## 운영 권장

기존 Codex/Claude 한 메인 세션이 작업을 지휘하고, 상태는 team-work, 대안 평가는 candidate-run, 승인과 공통 규칙은 기존 게이트/review-loop가 담당한다. 후보는 별도 사본에서 실행하고 원본 산출물과 판정을 남긴다. 원본 Hermes/Harness²의 추가 도입보다 이 흐름을 실제 프로젝트에서 반복해 측정하는 것이 현재 우선순위다. 실행 흐름과 담당 파일은 [구조 설명](team-architecture.md), 명령은 [사용 안내](team-work.md)에 있다.
