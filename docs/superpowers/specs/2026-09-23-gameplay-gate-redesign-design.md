# ④ 게임성 검증 규칙 변경 — 밸런스를 게이트에서 내린다

- 날짜: 2026-09-23
- 대상 버전: v0.35.0
- 상태: 설계 승인 후 2026-11-05 v0.51.0에 구현. 아래 내용은 당시 설계 기록이다.
- 구현 보완: 필수 소비량 합산, 빈 모델·잘못된 입력의 측정 불가, 시작 시 예산 예약, 기록 쓰기 잠금. 현재 계약은 `skills/balance-sim/references/clearability.md`와 `skills/playtest-capture/SKILL.md`를 따른다.

---

## 1. 문제

사용자 보고(2026-09-23):

> 밸런스를 너무 초반에 집착한다. 시뮬 결과랑 실제 플레이 체감이 아예 다르다.
> 저번에는 **5시간 동안 난이도에 집착**했는데 실제로 플레이하니 **게임이 그냥 끝나버렸다.**
> 토큰만 날리는 경우가 많다.

핵심 비용은 **검증의 부정확함이 아니라 토큰과 시간**이다. 실패 모드는
**사람이 게임을 만지기 전에 자동 루프가 너무 오래 돈다**는 것이다.

## 2. 왜 지금 구조가 이걸 만드나

### 2-1. 규칙은 이미 알고 있는데 구조가 따로 논다

`ORCHESTRATION.md` §3과 README는 이미 이렇게 쓰여 있다:

> ④는 봇(`balance-sim`)과 사람(`playtest-capture`) 둘 다 필요하다. 봇 지표만 충족이면 조건부다.

그런데 같은 문서가 **진행을 막는 권한은 시뮬에만 준다**:

> ③↔④ 반복 루프. 시뮬 지표 미달 시 ①(기획)으로 되돌려 재조정. 재미 전에는 ⑤로 안 감.

사람 축은 "있으면 좋은 것"이고, 루프를 돌리는 건 시뮬 수치다. 집착은 여기서 나온다.

### 2-2. 난이도는 봇에 대해 상대적인데 절대 수치처럼 나온다

`policies.mjs`의 봇은 반응속도·정보·실수율이 사람과 다르다. 봇 기준 승률 50%가
사람 기준 5%일 수도 95%일 수도 있다. **판수를 늘려도 이 격차는 줄지 않는다** —
정밀도 문제가 아니라 측정 대상이 다른 문제다. 5시간을 태워도 안 좁혀지는 이유다.

### 2-3. 모델이 실제 빌드와 갈라져도 아무것도 안 잡는다

*"실제로 플레이하니 게임이 그냥 끝나버림"* 은 원래 검사가 잡았어야 한다.
못 잡은 건 `game.mjs` 모델이 실제 빌드와 갈라졌기 때문이다. 지금 `PLACEHOLDER`
가드는 *"구현 안 됨"* 만 잡고 *"틀리게 구현됨"* 은 못 잡는다. 이게 가장 비싼 실패다 —
5시간이 통째로 허구가 된다.

## 3. 설계 결정

| # | 결정 | 근거 |
|---|---|---|
| D1 | ④에서 자동으로 도는 건 **클리어 가능성 검사**뿐 | 데이터 검사라 판수 0. 봇 정책에 의존하지 않는다 |
| D2 | ④ 통과 판정은 **사람 플레이** | 재미·난이도 체감은 봇이 구조적으로 못 잰다 |
| D3 | 디테일 밸런스는 **파이프라인 단계가 아니라 요청형** | 에이전트가 자율적으로 튜닝 루프를 시작하지 못하게 |
| D4 | 예산 강제를 **훅이 아니라 도구 안**에 | §10 "같은 도구 = 어느 하네스에서도 같은 결과" |
| D5 | 카운터를 두지 않고 **`playfeel.md` 로그가 곧 카운터** | 파일 하나, 사람이 읽을 수 있고, 위조가 같은 화면에 보인다 |

### D1 상세 — 왜 "논리적 클리어 불가"만인가

처음 안은 하한선에 `승률 0%/100%`, `단일 전략 픽률 >90%` 를 넣었다. 뺐다. 이유:

- 둘 다 **여전히 시뮬을 수백 판 돌려야** 나온다 (토큰이 든다)
- 둘 다 **여전히 봇 기준**이다. 승률 0%가 게임 탓인지 봇이 못하는 건지 구분이 안 된다
- 픽률 편향은 논리 문제가 아니라 밸런스 문제다 — D3에 따라 사람이 요청할 때 본다

"논리적으로 클리어 불가"는 **플레이어 실력과 무관**하다. 그래서 봇 문제가 사라진다.
그리고 설계 데이터를 직접 검사하므로 **2-3의 모델 괴리 문제도 우회된다** —
검사 대상이 실제로 출시되는 테이블 자체다.

**못 잡는 것(의도된 한계):** 논리적으로는 가능한데 실질적으로 불가능한 경우.
반응시간 50ms가 필요한 패턴, 완벽한 플레이로만 맞는 자원 수지 등.
이건 사람이 한 판 하면 바로 안다 — D2와 일관된다.

### D4 상세 — 훅을 왜 뺐나

초안은 `PreToolUse`/`Bash` 차단 훅이었다. 사용자가 "Codex랑 Claude Code를 왔다 갔다
한다, 싱크 맞춰달라"고 해서 다시 봤더니 §10에 이미 답이 있었다:

> ① 같은 도구 — 아트 도구는 전부 의존성 0의 결정론적 Node 스크립트다.
> 모델이 결과를 만들지 않으므로 어느 하네스에서 돌려도 같은 결과가 나온다.

훅은 이 원칙을 어긴다. 도구 안으로 옮기면:

1. **하네스 무관** — Codex · Claude Code · 사람이 터미널에서 직접, 전부 같게 동작
2. **훅보다 촘촘하다** — 훅은 Claude Code의 Bash 도구를 탈 때만 발화한다.
   다른 경로로 돌리거나 사람이 직접 돌리면 안 잡힌다. 도구 안이면 항상 잡힌다
3. **차단형 훅이라는 새 위험을 안 만든다** — 이 레포에 차단 훅은 지금까지 0개다

## 4. 변경 후 규칙

| | 지금 | 바뀐 뒤 |
|---|---|---|
| ④에서 자동으로 도는 것 | `balance-sim` (수백~수천 판) | `clearability` 검사 (판수 0) |
| ④ 통과 판정 | 시뮬 지표 | **사람 플레이** |
| 난이도 | 시뮬이 판정 | **시뮬은 판정하지 않는다** |
| 디테일 밸런스 | 파이프라인 단계 | **요청형 도구** |
| ③↔④ 루프 반환 조건 | 시뮬 지표 미달 | **클리어 논리 불가일 때만** |
| 시뮬 실행 예산 | 없음 | **마지막 사람 플레이 이후 2회** |

`balance-sim`은 **삭제하지 않는다.** 자동 실행에서 빠져 요청형이 될 뿐이다 —
수치를 정말 조일 때는 여전히 제일 좋은 도구다.

`econ-sim`(⑨ 경제)은 **건드리지 않는다.** 무과금 완주율·페이투윈 격차는 30일치
축이라 사람이 티키타카로 못 느낀다. 게이트 권한을 유지한다.

## 5. 새 도구 계약

### 5-1. `clearability` — 논리적 클리어 가능성

장르 무관하게 셋으로 환원된다:

| 검사 | 미달 예 |
|---|---|
| 자원 수지 | 보스 체력 500인데 획득 가능 총딜 420 |
| 도달성 | 잠금 그래프 순환(A는 B가, B는 A가 필요) · 고립 노드 |
| 순서 제약 | 위상 정렬 불가 |

스캐폴드가 `sim/clearability.mjs` 를 깔고, 프로젝트는 **실제 테이블 → 요구/공급 매핑**만 쓴다:

```js
// sim/clearability.mjs  (스캐폴드가 생성, 프로젝트가 채운다)
import { STAGES } from '../src/data/stages.js';   // 실제 테이블을 읽는다

export const PLACEHOLDER = true;                  // 채우면 false 로 바꾼다

export function model() {
  return {
    supply:  { damage: totalDmg(STAGES), keys: 2 },
    require: [{ id: 'boss', needs: { damage: 500 } }],
    locks:   [{ id: 'door2', needs: ['key1'] }],
    order:   [['tutorial', 'stage1'], ['stage1', 'boss']],
  };
}
```

종료 코드: `0` 충족 / `1` 미달(논리적 클리어 불가) / `3` 측정 불가(미구현·모델 불충분).

**실제 테이블을 읽으므로 드리프트가 없다.** 선언 파일을 따로 두는 안은 기각했다 —
수치가 바뀌는데 선언을 안 고치면 검사가 조용히 거짓말을 한다.

### 5-2. `playfeel` — 한 줄 로그이자 예산 장부

```bash
node <플러그인>/skills/playtest-capture/scripts/playfeel.mjs record --felt "2페이즈에서 손이 멈춤"
node <플러그인>/skills/playtest-capture/scripts/playfeel.mjs log
```

수치 변경은 git diff에서 자동으로 묶는다. 사람이 쓰는 건 한 문장뿐이다.

**위치는 프로젝트 루트의 `playfeel.md` 로 고정한다.** `sim/` 안에 두지 않는다 —
사람이 읽는 장부이고, 밸런스 하네스를 안 쓰는 프로젝트도 쓸 수 있어야 한다.
`run.mjs` 는 자기 위치에서 위로 올라가며 찾는다(`sim/` → 프로젝트 루트).

`playfeel.md` 형식:

```
#7  hp 20->16, 보스dmg 5->7
    [사람] "2페이즈에서 손이 멈춤. 긴장도 맞는듯"
    [시뮬] seed 42 runs 200 -> 승률 61%
    [시뮬] seed 42 runs 200 -> 승률 54%
    [시뮬] 차단 — 마지막 플레이 이후 2회를 썼다
```

바퀴 번호(`#7`)는 `playfeel record` 가 자동 증가시킨다. 사람이 세지 않는다.

**기록과 예산 리셋이 한 명령이다.** 따로 두면 "기록 없이 리셋"이 가능해진다.

### 5-3. `run.mjs` 예산 — 도구가 스스로 막는다

스캐폴드가 생성하는 `sim/run.mjs` 가 시작할 때 `playfeel.md` 를 읽어
**마지막 `[사람]` 줄 이후의 `[시뮬]` 줄 수**를 센다. 2 이상이면 판정 없이 `exit 3`:

```
[시뮬] 예산 차단 — 마지막 플레이 이후 시뮬 2회를 썼다.
난이도는 봇 기준이라 더 돌려도 사람 난이도에 가까워지지 않는다.
한 판 하고 playfeel record 로 한 줄 남겨라.
```

`[사람]` 줄이 한 번도 없으면 전체 `[시뮬]` 줄을 센다(첫 플레이 전에도 예산이 산다).

`playfeel.md` 가 아예 없으면 **예산 검사를 건너뛴다** — 이 규칙을 안 쓰는 프로젝트에
소음을 만들지 않는다(레포 원칙: 게임 프로젝트가 아니면 소음 0).

**`exit 3` 이 두 가지 의미로 쓰이는 점에 주의한다.** 자리표시자(`PLACEHOLDER`)도 3,
예산 차단도 3이다. 둘은 리포트 본문으로 구분한다 — 자리표시자는 5섹션 리포트에
`측정 불가` 판정을 쓰고, 예산 차단은 `예산 차단` 문구를 쓰고 5섹션 리포트를 내지 않는다.
CI가 이 구분을 검사한다(§7).

**예산은 세션이 아니라 플레이 단위다.** 사람이 한 판 할 때마다 시뮬 2회.
이게 티키타카를 규칙이 아니라 구조로 만든다.

## 7. 검증 (CI)

| 검사 | 통과 조건 |
|---|---|
| `clearability` 미구현 | `exit 3` (측정 불가) — 통과가 아니다 |
| 자원 수지 부족 | `exit 1` + 부족한 자원과 수치 보고 |
| 잠금 그래프 순환 | `exit 1` + 순환 경로 보고 |
| 순서 제약 위배 | `exit 1` |
| 정상 모델 | `exit 0` |
| 예산 — 마지막 플레이 후 1회째 | 정상 실행 |
| 예산 — 2회째 | 정상 실행 |
| 예산 — 3회째 | `exit 3` + 본문에 `예산 차단`, **5섹션 리포트 없음** |
| 자리표시자 + 예산 여유 | `exit 3` + 본문에 `측정 불가`, **5섹션 리포트 있음** |
| `playfeel record` 후 | 예산 리셋, 다시 실행됨 |
| `playfeel.md` 없음 | 예산 검사 건너뜀 (침묵) |

마지막 두 줄이 중요하다. `exit 3` 이 자리표시자와 예산 차단 두 곳에서 나오므로,
**종료 코드만 보는 검사는 둘을 구분하지 못한다.** CI는 본문 문구까지 대조해야 한다.

기존 CI 스텝(밸런스 하네스 왕복)은 `playfeel.md` 없이 도므로 영향받지 않는다 —
그 사실 자체를 검증에 넣는다.

## 8. 잔여 위험 (정직하게)

- **도구는 사람이 실제로 플레이했는지 검증할 수 없다.** 에이전트가 `playfeel record`
  를 지어내면 예산이 리셋된다. 완전히 막을 방법이 없다. 대신 **`playfeel.md` 한 파일에
  사람 기록과 시뮬 기록이 같이 쌓이므로 위조가 눈에 보인다.** 이게 이 설계가 할 수 있는
  최선이고, 한계로 문서에 남긴다.
- **논리적으론 가능한데 실질적으로 불가능한 경우**는 못 잡는다(D1 상세 참고).
  사람 플레이가 잡는다.
- **`clearability.mjs` 매핑이 틀리면 검사도 틀린다.** 실제 테이블을 읽게 해서
  드리프트는 막았지만, 매핑 자체의 오류는 못 막는다. 미구현은 `exit 3`로 잡히지만
  **잘못 구현은 안 잡힌다** — `game.mjs` 와 같은 한계가 축소된 형태로 남는다.
