# 갇힌 배경 검출 — 사지 사이에 남는 배경을 잡는다

- 날짜: 2026-11-03
- 대상 버전: v0.52.0
- 상태: 설계 (구현 전)
- 스파이크: 2026-11-03 세션. 측정 결과가 본문 전반의 근거다.

---

## 1. 무엇을 고치나

ComfyUI 로 뽑은 캐릭터에서 **다리와 다리 사이, 팔과 몸통 사이의 흰색이 안 지워진다.**
GPT 내장 `image_gen` 경로는 거의 정상이다.

이건 버그가 아니라 **의도된 설계의 대가**다. `cutout.mjs` 머리말에 이렇게 쓰여 있다:

> **테두리에서만 번져 들어가는** flood fill 을 쓴다 — 바깥과 이어진 배경만 지우고,
> **안쪽에 갇힌 흰색은 남는다.**

"흰색을 지워라"로 했다가 흰 튜닉 캐릭터의 옷이 뚫린 적이 있어서 그렇게 바꿨다.
그 보호의 비용이 지금 문제다. GPT 경로가 멀쩡한 이유도 같은 선이다 — **알파를 네이티브로
받아 컷아웃을 아예 안 거친다.**

## 2. 의도와 성공 기준

**의도**: 사지에 둘러싸여 남은 배경을 **찾아서 사람에게 보여준다.** 자동으로 지우는 게 아니다.

**성공**: 위 walk_05 같은 프레임에서 들린 다리·칼날·부츠·코트에 둘러싸인 흰 영역이
리포트에 뜨고, 미리보기 PNG 에 표시된다. 흰 옷·칼날 속살은 뜨지 않는다.

## 3. 목표 / 비목표 / 반(反)목표

**목표**
- 갇힌 배경 후보를 검출하고 위치·크기·색을 리포트에 낸다
- 사람이 눈으로 확인할 수 있는 표시 이미지를 낸다
- 명백한 경우에 한해 **옵트인**으로 제거한다

**비목표**
- `cutout.mjs` 의 flood fill 을 교체하지 않는다. 그건 지금 잘 돌고 있다
- 애니메이션·리깅 판정은 범위 밖이다(별건, REVIEW 열린 항목)
- 배경과 **같은 색**의 옷을 자동으로 가려내지 않는다 — 불가능하다(§5)

**반목표 (이렇게 되면 기능이 동작해도 실패다)**
- **기본값으로 자동 제거.** 흰 배경 + 흰 튜닉에서 옷을 지우게 된다. 레포가 이미 겪은 사고다
- 수치만 통과하고 눈으로는 깨진 산출물. §6 이 이것 때문에 있다

## 4. 측정으로 확정된 것 (스파이크 결과)

### 4-1. rembg 는 답이 아니다 — 그리고 필요 없다

| 시도 | 갇힌 배경 | 흰 옷·얇은 부위 |
|---|---|---|
| `rembg` (u2net) 단독 | 지움 | **반투명으로 먹음** — 반투명 0.3% → **3.0%** |
| 기하(연결성)만 쓰는 하이브리드 | 일부 | **칼끝을 뚫고 흰 바지를 지움** |
| **기하 + 배경색 일치** | **정확히 그것만** | 건드리지 않음 |

세 번째는 **의존성 0**이다. 176MB ONNX 모델과 `onnxruntime` 이 필요 없다.
rembg 를 설계에서 뺀 건 취향이 아니라 **측정 결과**다.

### 4-2. "밝다" 와 "배경색이다" 는 다르다

첫 시도에서 "갇힌 **밝은** 영역"을 세고 그걸 배경이라 불렀다. 틀렸다:

```
제거된 배경 평균    rgb(187,188,184)
후보 덩어리들       rgb(~235,230,222)   거리 54~68   <- 배경 아님. 흰 바지·소매였다
```

판별 조건은 **검출된 배경색과의 거리**다. 밝기가 아니다.

### 4-3. 잘린 RGBA 만으로는 배경색을 복원할 수 없다

알파 0 인 픽셀의 RGB 가 0 으로 뭉개진 산출물이 있다. 그런 파일에서 배경색을 추정하면
`rgb(0,0,0)` 이 나오고, 피사체의 검은 외곽선이 전부 "갇힌 배경"으로 잡힌다(실측:
`sprite-lab` 전 세트가 거짓 양성).

→ **검출은 원본 RGB 를 볼 수 있는 자리에서 해야 한다.**

### 4-4. 실제 검출 규모 (higgsfield walk 6프레임)

```
walk_00   969px (43x106)      walk_03  1407px (56x44)
walk_01   388px (27x54)       walk_04  3197px (93x75)
walk_02   110px (10x21)       walk_05  5515px (114x104)
```

프레임마다 0~6 개, 최대 캔버스의 0.6%. 세로로 긴 것(43x106)이 다리 사이,
넓은 것(114x104)이 들린 다리·무기·부츠에 둘러싸인 공간이다.

## 5. 못 하는 것 (설계 한계 — 숨기지 않는다)

**배경과 같은 색의 옷은 색으로 가릴 수 없다.** 흰 배경 + 흰 튜닉이면 갇힌 배경과 옷이
같은 색이고, 둘 다 사지에 둘러싸일 수 있다. 기하로도 색으로도 구분되지 않는다.

그래서 이 도구는 **판정하지 않고 보고한다.** 사람이 미리보기를 보고 정한다.
이건 회피가 아니라 이 레포의 원칙(최종 권위자는 사람)과 같은 자리다.

## 6. 설계

### 6-1. 어디에 넣나

**`cutout.mjs` 안**이다. 이유는 §4-3 — 배경색을 알려면 원본 RGB 가 필요한데,
`cutout.mjs` 는 이미 원본을 읽고 배경색을 검출해 쥐고 있다. 별도 도구로 빼면 원본을
다시 받아야 하고, 안 받으면 거짓 양성이 난다.

`cutout.mjs` 는 "만드는 도구"지만 이미 판정성 경고를 낸다(`!! 캐릭터가 뚫렸다`).
갇힌 배경 보고는 그 자리에 붙는다.

### 6-2. 검출 규칙

컷아웃 결과에서 아래를 **모두** 만족하는 연결 성분:

1. **불투명** (alpha > 128)
2. **검출된 배경색과 일치** — 채널별 차이 <= `--hole-tol` (기본 35)
3. **테두리에 안 닿음** (갇혀 있음)
4. **최소 크기 이상** — `--hole-min` (기본 60px). 그 아래는 안티에일리어싱 잔여물이다

### 6-3. 모호 판정

후보의 평균색이 **큰 불투명 피사체 영역의 색과도 가까우면** 모호하다
(흰 배경 + 흰 옷). 모호한 후보는 **제거 대상에서 빼고 `측정 불가`로 따로 보고**한다.
`--fill-holes` 를 줘도 모호한 것은 안 지운다.

> 구현자 판단 영역: "큰 피사체 영역"의 정의. 가장 단순하게는 테두리에 닿는 최대 불투명
> 성분의 색 히스토그램과 대조한다. 더 나은 방법이 있으면 써도 된다 — 판정 결과만
> 보수적이면 된다(모호하면 안 지운다).

### 6-4. 출력

- **리포트 한 줄 추가**: `갇힌 배경 N개 (최대 5515px 114x104) · 모호 M개`
- **표시 PNG**: `--out` 디렉터리에 `<이름>_holes.png`. 후보를 빨강으로 칠한 미리보기.
  스파이크에서 이 이미지 하나로 사람이 즉시 판단할 수 있었다
- **종료 코드는 바꾸지 않는다.** 갇힌 배경이 있다고 컷아웃이 실패한 건 아니다.
  경고만 낸다 — 기존 `!! 캐릭터가 뚫렸다` 와 같은 급이다

### 6-5. 제거 (옵트인)

`--fill-holes` 를 주면 모호하지 않은 후보의 알파를 0 으로 만든다.
**기본값은 끔.** §3 반목표.

## 7. 검증 (CI)

| 검사 | 통과 조건 |
|---|---|
| 갇힌 배경이 있는 픽스처 | 검출 수 >= 1, 위치가 기대 좌표 안 |
| 갇힌 배경이 없는 픽스처 | 검출 0 (오탐 0) |
| **배경색과 같은 색의 "옷" 픽스처** | **모호로 분류**, `--fill-holes` 를 줘도 안 지움 |
| `--fill-holes` 적용 후 | 해당 영역 alpha 0, 그 외 알파 불변 |
| 표시 PNG | 생성되고, 빨강 픽셀 수 == 검출 픽셀 수 |

픽스처는 합성으로 만든다(절차적 PNG). 실제 아트를 CI 에 넣지 않는다.

**오탐이 곧 게이트 고장이다.** 두 번째 줄(오탐 0)이 가장 중요하다.

## 8. 눈으로 확인하는 단계를 빼지 마라

스파이크에서 **수치가 전부 통과하는데 결과가 틀린 경우가 두 번** 나왔다.
연결성 하이브리드는 반투명 비율 0.02 로 기존과 동일했지만 칼끝에 구멍이 나 있었다.
확대 이미지를 보기 전까지 몰랐다.

그래서 구현 중 다음을 **반드시** 한다:
- 후보를 표시한 PNG 를 만들고 **실제로 열어 본다**
- 흰 옷이 있는 캐릭터 1장, 갇힌 배경이 있는 캐릭터 1장을 최소 샘플로 쓴다
- 수치만 보고 "통과"라고 적지 않는다

이 레포의 관측 로그에 "검사는 통과하는데 눈으로는 이상하다"가 8건 쌓여 있다.
이 작업은 그 부류를 고치는 작업이지 새로 추가하는 작업이 아니다.

## 9. 구현자에게 남기는 것

- §6-3 "큰 피사체 영역"의 구체적 정의
- `--hole-tol` 35 · `--hole-min` 60 의 보정. 스파이크는 두 값으로 실제 사례를
  잡았지만 샘플이 적다. CI 픽스처와 실제 아트 몇 장으로 다시 재라
- 표시 PNG 의 체커보드 위상. 스파이크에서 패널마다 위상이 달라 눈 비교가 어려웠다
- 한 이미지에 후보가 20개 넘게 나올 때의 리포트 축약 방식
