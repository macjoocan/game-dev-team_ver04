# 기획·개발 후보 비교 하네스 도입 설계

날짜: 2026-10-24
상태: 검토용 설계. 구현·설치·실제 모델 실행 전. 범위 승인은 이 문서에 대해 받는다.
대상 소스: GameDevTeam 0.47.1, `712e3f3`.

## 1. 목적과 근거

사용자 요구: Harness²의 구조를 기획·개발에도 도입한다. 현재 3D에 있는 후보 비교 절차를 공통 실행·증거 계약으로 확장한다.

- [Harness²](https://github.com/google-research/harness2), 조사 리비전 `1cfe254e8d25b15f37048c3730134686abe60335`.
- [실험·재개 구조](https://github.com/google-research/harness2/blob/1cfe254e8d25b15f37048c3730134686abe60335/docs/EXPERIMENTS.md).
- 기존 `skills/asset-3d-pipeline/references/propose-probe-compose.md`, `ORCHESTRATION.md`의 게임성·정확성·사람 승인 계약을 활용한다.

원본의 Propose–Probe–Compose와 증거 기반 경험 재사용에서 착안한 독립 구현이다. 원본 소스·의존성·벤치마크는 반입하지 않는다. 게임 성능 개선 수치는 아직 없다.

## 2. 두 비교 축

Harness²의 중심은 산출물뿐 아니라 작업 방식 자체를 개선하는 것이다. 이를 구분해 기록한다.

| 축 | 후보로 바꾸는 것 | 고정할 것 |
|---|---|---|
| `artifact` | 기획 규칙·데이터 또는 개발 구현 | 과제·평가 기준·입력·검증 도구 |
| `workflow` | 사용하는 스킬·도구 안내·작업 순서 | 과제·요구·평가 기준·테스트·게임 데이터 |

한 비교에서 두 축을 섞지 않는다. 기준안 1개와 대안 1~2개를 비교하고, 합성안은 실제로 다시 실행한다. 각 후보는 별도 폴더 또는 체크아웃에 준비한다. 실행기가 제품 코드를 자동 수정하거나 LLM을 호출하지 않는다.

1차 `workflow` 후보의 실행자는 메인 세션이다. 메인 세션이 후보별 작업 지침·스킬/도구 버전 스냅샷을 준비하고, 같은 과제를 순차 수행해 결과를 별도 후보 폴더에 보존한다. 각 후보에 workflow-spec 해시, 실행 세션 식별자, 실제 사용 도구·모델(알 수 없으면 unknown), 시작/종료 시각, 추적 로그·산출물 경로를 포함한 execution-evidence.json을 남긴다. CLI는 이 실행 증거와 산출물 해시를 검사한 뒤 공통 검증만 실행한다. 기록 없는 준비 파일은 workflow 개선의 증거로 인정하지 않는다. 기존 출력만 검증한 경우에는 검증 결과 비교라고 표시한다. 외부 LLM 실행기 어댑터·자동 세션 시작은 1차 범위에 없다. workflow 조건을 분리할 수 없으면 그 비교는 미실행으로 남기고 artifact 비교부터 진행한다.

## 3. 사용 범위

- 의미 있는 대안이 있고 비교 근거를 만들 수 있는 결정에만 사용한다. 단순 수정·정답이 정해진 설정은 바로 처리한다.
- 기획: 전투 규칙, 보상 간격, 난이도 곡선 등. 필러와 성공 지표를 먼저 정한다. 한 회차 조정 노브는 기존 규칙대로 최대 2개다.
- 개발: 상태 관리, 로딩, 저장, 리팩터 등. 같은 기능 계약·테스트를 유지한 후보를 비교한다.
- 기획 문서의 완결성·재미·코드 정확성은 서로 다른 판정이다. GDD 검수·시뮬·사람 플레이·QA의 기존 역할을 유지한다.
- 1차는 현재 세션이 순차로 실행한다. 병렬 에이전트, 모델 라우터, 무인 자기수정, 자동 배포는 추가하지 않는다.

## 4. 실행 계약

Node 표준 라이브러리로 공통 CLI `scripts/candidate-run.mjs`를 추가한다. 프로젝트는 `docs/experiments/<id>/experiment.json`으로 과제와 검증 명령을 지정한다.

필수 정보:

- stable experiment ID, `planning`/`development`, `artifact`/`workflow`, 목적과 판단 질문.
- 목표·필러·요구 문서 경로와 내용 해시. 목표가 잠정이면 상태와 근거를 명시한다.
- 기준 후보 ID와 후보 목록, 차이 설명, 후보별 명시적 cwd와 산출물 경로.
- 소스 커밋과 dirty 상태, 비교에 영향을 주는 소스·설정·입력 파일의 해시 목록. dirty 입력도 해시로 고정한다.
- 검증 명령은 executable + args 배열과 timeout으로 표현한다. 기본 shell=false. 후보의 명령은 같은 검증 정의를 사용하고 경로만 후보 루트로 해석한다.
- 시드·정책·판수·기기·엔진·런타임 버전 등 비교 조건. 해당하지 않는 값은 이유와 함께 제외한다.
- 필수 검증, 비교 지표의 방향·단위·임계값·근거. 임계값이 없으면 순위 참고값이며 게이트 통과로 쓰지 않는다.
- 시간·시도 수·필요하면 API 비용 상한. 1차는 유료 API나 모델 실행을 자동 호출하지 않는다.

검증 명령이 실제 코드 실행 권한을 가진다는 점을 명시한다. 신뢰하는 프로젝트 설정만 사용하고 기존 실행 권한·샌드박드는 유지한다. 범위 밖 경로의 수정·삭제는 실행 계약으로 허용하지 않는다.

## 5. CLI와 산출물

| 명령 | 동작 |
|---|---|
| `init --domain planning|development --out <path>` | 과제별 템플릿 생성. 필수 미정값을 남기며 실행 가능으로 위장하지 않음 |
| `check <experiment.json>` | 경로·검증·예산·후보·비교 조건 검사. 모델 호출 없음 |
| `run <experiment.json> [--resume]` | 기준안부터 순차 실행, 원시 로그·시각·종료 코드·산출물 해시 저장 |
| `report <experiment.json>` | 같은 조건의 후보를 비교표로 출력. 자동 채택·승인 없음 |
| `record <experiment.json> --candidate <id> --reason <text>` | 선택 제안을 별도 decision.json으로 기록. 사람 승인·merge 상태를 변경하지 않음 |

프로젝트의 `out/experiments/<id>/<run-id>/` 아래에 계약 스냅샷·후보별 stdout/stderr·프로세스 결과·정규화된 검증 결과·JSON/Markdown 리포트를 남긴다. 원시 로그는 변형하지 않는다. 보고서에는 기존 5섹션(주장·증거·기준·공백·잔여 위험)을 둔다.

run-id는 시간과 충돌 방지 suffix로 생성한다. `run`은 기존 실행을 덮어쓰지 않는다. `--resume`은 단일 진행 실행을 식별해 잠금을 얻고, 계약·입력·검증·도구 버전 해시가 같을 때 완료 증거만 재사용한다. 달라졌으면 새 실행을 요구한다. 같은 실행에 두 작성자가 접근하면 거부한다.

`running` 도중 종료된 명령은 다음 세션에서 `interrupted`로 표시한다. 자동 재전송하지 않는다. 후보 명령은 기본적으로 재실행 금지이며, 사용자가 로컬 검증에 한해 `retrySafe: true`로 선언한 경우만 재실행한다. 외부 변경의 성공 여부가 불명확하면 수동 확인이 필요하다. 실행 ID는 외부 작업의 중복 방지를 보장하지 않는다.

## 6. 판정과 측정

- 기존 도구 계약을 유지한다: `0` 충족, `1` 미달, `3` 측정 불가. CLI의 설정 오류도 설명과 함께 `3`으로 반환한다.
- 일반 테스트의 비0 종료는 곧바로 기획 미달로 간주하지 않는다. 프로세스 오류·timeout·누락 증거는 측정 불가이며, 어댑터가 명시한 테스트 실패만 해당 검증 미달로 정규화한다.
- 집계: 필수 검증에 하나라도 확인된 미달이 있으면 1, 확인된 미달은 없지만 필수 측정이 빠지면 3, 모두 충족이면 0. 개별 미달·공백은 집계와 관계없이 전부 노출한다.
- 문서 검수와 사람 판정은 자동 명령으로 가장하지 않는다. 대상·내용 해시가 맞는 증거 파일을 연결하고, 미연결 시 측정 불가로 남긴다. 공통 형식은 evidence ID·유형·검증자·대상 해시·시각·원시 증거 경로·상태를 포함한다. 등록 명령은 증거를 입력받을 뿐 사람 신원을 자동 인증한다고 주장하지 않는다.
- 검증 계약과 지표 추출기는 후보가 수정할 수 없다. 고정된 평가 경로·내용 해시가 달라지면 해당 비교는 무효다. 검증 파일을 후보별로 복제했다면 기준 해시와 같아야 한다.

### 기획 어댑터

기존 balance-sim 출력을 읽는다. 스캐폴드를 새로 만들지 않고 프로젝트 `simulateRun`을 사용한다. PLACEHOLDER, 표본 부족, 실행 오류는 3이다. 동일 정책·판 시드로 A/B를 맞추되, 분기 차이로 RNG 소비가 달라지면 완벽히 동일한 난수 경로라고 주장하지 않는다. 기존 95% 구간 판정은 유지하며 후보 간 차이의 통계적 유의성을 자동 주장하지 않는다.

GDD 검수와 사람 플레이 결과를 별도 증거로 연결한다. 봇 수치가 좋아도 사람 플레이가 없으면 재미 승인은 미완료다. 후속 과제에 적용할 때는 조건이 다른 새 비교로 시작한다.

### 개발 어댑터

프로젝트가 가진 테스트·빌드·스모크·성능 명령을 연결한다. 보편적인 게임 테스트를 새로 발명하지 않는다. 성능 비교는 같은 런타임·기기·입력·반복 수를 요구하고 워밍업·중앙값 등 방법을 기록한다. 단일 실행이면 관측값으로만 보고한다. 이 계약을 고정할 수 없으면 성능 비교는 3이다.

QA와 pr-review의 판정·사람 merge 승인은 유지한다. 테스트 통과로 재미나 아트 승인을 대신하지 않는다.

## 7. 지속 개선과 정본

실험 결과에는 두 기록을 둔다: 프로젝트 후보의 채택 제안과, 재사용 가능한 작업 방법의 lesson 제안이다. lesson은 해당 과제·입력·도구 버전·효과·실패 조건·반례·증거 경로를 가진다. 상태는 `proposed`/`accepted`/`rejected`이며, 생성 시 proposed다. 공통 스킬 개선은 task-observer의 고정 로그·staging·검토 절차로 넘기며 이 CLI가 스킬을 자동 편집하지 않는다.

다음 과제의 lesson 조회·조건 판단·적용 책임도 1차는 메인 세션에 둔다. 시작할 때 프로젝트의 `docs/experiments/lessons/`와 해당 분야 스킬의 lessons를 읽고, 스킬 개선 관찰은 기존 task-observer 절차로 조회한다. experiment.json의 lessonUses에 lesson ID·파일 해시·원래 증거 경로·적용 조건·이번 적용 또는 제외 이유를 남긴다. 읽을 교훈이 없으면 명시적 빈 배열과 조회한 경로를 기록한다. CLI의 check는 이 intake 기록의 존재와 참조 해시를 검사하며, 내용이 바뀐 lesson을 조용히 재사용하지 않는다. 프로젝트 lesson의 accepted 상태는 사람 결정의 증거 경로를 요구하고 CLI가 승격하지 않는다. proposed는 가설로만 사용할 수 있다. 자동 검색·랭킹·전역 메모리 동기화는 추가하지 않는다. 이로써 지속 개선은 사람이 검토하는 실행 절차이며, 자동 자기학습 기능이라고 보고하지 않는다.

`.review-loop/`는 기존 사람의 산출물 승인 정본이다. 비교 리포트는 링크하고 승인 정보를 복제해 별도 정본으로 만들지 않는다. `state.json`, `PIPELINE_STATE.md`, 기존 거절·승인 상태를 CLI가 수정하지 않는다. review-loop의 summary가 상태를 조정할 수 있으므로 조회를 가장한 자동 동기화도 넣지 않는다.

## 8. 구현 범위와 배포

1차 변경: 공통 CLI·단위 테스트, 기획/개발 어댑터 계약·예제, ORCHESTRATION의 사용 조건, 관련 기존 스킬의 짧은 연결 안내. 새 스킬을 중복 추가하지 않는다. 예제는 모델 호출 없는 로컬 fixture로 만들고 합성 결과라는 표시를 유지한다.

스킬 파일 변경 전 skill-authoring 지침을 읽고 필요한 staging 절차를 따른다. 배포 시 버전은 0.48.0을 제안하되 최신 원격과 충돌 여부를 확인해 결정한다. 정본에서 mirror를 공식 스크립트로 갱신하고 validate-plugin을 실행한다. CI를 변경하면 ci-local도 실행한다. 설치본은 공식 installer로 갱신한다. push·merge는 기존 사용자 권한·게이트 범위에 따른다.

## 9. 수용 기준과 검증 범위

- 기준안·대안이 같은 과제·검증 계약 아래 실행되고, 고의로 변경한 평가 해시를 거부한다.
- timeout, 자식 프로세스 정리, 경로 오류, 0/1/3, 누락 로그, 중단·재개, 동시 실행 잠금, 조건 변경을 테스트한다.
- 기준안 통과·대안 미달과 기준안 미달·대안 개선 사례를 모두 fixture로 재현한다.
- 합성 후보의 재실행 전 결과를 채택 근거로 사용할 수 없다.
- 사람 플레이가 없는 기획, 실행하지 않은 QA, 다른 산출물 해시의 승인은 충족으로 표시하지 않는다.
- 실제 게임 파일은 이 플러그인 저장소에서 소유하지 않는다. 1차 검증은 fixture이며 실제 게임 품질 향상을 증명하지 않는다. 실제 게임 pilot은 사용자가 지정한 프로젝트에서 별도로 실행한다.

남은 사용자 결정: 이 문서의 1차 범위 승인. 엔진·기획 과제 선택은 공통 도구 구현을 막지 않는다. 그 밖의 schema 이름·테스트 파일 배치는 구현자가 정하되 위 계약을 지킨다.

## 10. 독립 검토 기록

brainstorming의 Builder Check로 독립 검토했다. 두 미결점(workflow 실행자, 교훈 조회 책임)을 확인해 위 §2·§7에서 메인 세션의 명시적 책임과 입력 계약으로 해결했다. 구현 범위를 외부 모델 자동 실행·자동 교훈 승격으로 넓히지 않는다. 검토는 설계의 계획 가능성 점검이며 실제 도구·게임 품질 검증은 아니다.
