## 북극성

> **기획자 혼자 게임을 만들 때, 아트를 대신 해주는 서포터.**

사람 본인 말(2026-09-18): *"나머지는 걱정이 없는데 아트가 젤 걱정이야."*
기획·밸런스·경제는 본인이 한다. **아트만 막힌다.** 그래서 이 축이 이 플러그인에서 값어치가 가장 높다.

목표 1(일반 2D)과 목표 2(도트)는 **수단**이고, 목표 3이 **목적**이다.
1과 2는 "무엇을 만드나", 3은 "누가 쓸 수 있나"를 정한다.

## "아트 한 벌"의 정의

목표 3이 달성됐다고 말하려면 산출물 단위가 있어야 한다. **한 벌 = 게임 하나가 굴러가는 최소 아트 세트:**

| | 수량 | 내용 |
|---|---|---|
| 캐릭터 | 주인공 1 + 적 3 + 보스 1 | 정지 · 걷기 · 공격 · 피격 |
| UI | 1세트 | 버튼 4상태 · 패널 · 바 · 아이콘 8 · 프레임 |
| 이펙트 | 1세트 | 타격 · 소멸 · 획득 · 충전 |
| 배경 | 타일셋 1종 | 바닥 · 벽 · 장식 |
| 출구 | 전부 | 시트 + manifest(프레임·fps·피벗·9-slice) |

**이 한 벌이 손 작업 0으로 나오면 목표 3 달성이다.** 두 번 나오면(일반 2D 한 벌 + 도트 한 벌)
목표 1·2도 같이 닫힌다.

### 2D 포즈와 3D 렌더의 분업 (2026-09-30 확정)

집에서 올라온 [2D 포즈 파일럿](../skills/char-art-system/references/pose-reference-pilot.md)이
같은 문제(포즈가 달라도 같은 캐릭터)를 2D 쪽에서 친다. **경쟁이 아니라 단계가 다르다:**

- **시안·탐색(2~4장) = 2D 포즈 파일럿** — 빠르고 싸다. 모델링이 필요 없다
- **양산(8~16프레임) = 3D 렌더** — 정체성이 구조적으로 보장된다

파일럿 스스로 8~16프레임 연속 동작은 미검증이라고 적었다. 시안에서 고른 것을 그대로 늘리지 않고,
고른 **디자인**을 3D 로 옮긴다. 3D 경로의 약점은 정체성이 아니라 **소스 모델 품질**이고
(사람 판정: "애니는 잘 나옴, 모델링이 구린 것"), 그건 조달 문제라 생성·라이브러리로 푼다.

**막힌 곳(2026-09-30):** Hyper3D 는 free_trial 키 잔액 0(`API_INSUFFICIENT_FUNDS`).
Poly Haven 은 켜졌지만 텍스처·HDRI 위주라 캐릭터가 없다. Poly Pizza(무료 키)와
Hunyuan3D(체크박스)가 미개통 — 여기가 열려야 3D 양산 축이 돈다.

## 서비스 버전까지 — 남은 로드맵 (2026-10-02 갱신)

**정적 축은 다 찼다.** 캐릭터 정지(일반 2D·도트) · 배경 · UI 규격 · 이펙트 기본 · 판정 · 출구.
`samples/tileset-v1/game-screen.png` 가 그 증거다 — 배경 위에 캐스트 4종이 같은 팔레트로 선다.

남은 것을 값어치 순으로:

| | 무엇 | 왜 지금 | 선행 |
|---|---|---|---|
| **1** | **걷기를 새 캐스트에 실제로 돌린다** | `walk-composite` 는 있는데 **cast-v2 에 미검증**이다. 도트에 되는지도 모른다 | 없음 |
| **2** | 공격·피격 모션 | 관절이 접혀야 한다. `rig-split` + Aseprite 이징 트윈 | 1 |
| **3** | 4·8방향 | Qwen-Image-Edit 턴어라운드 또는 PixelLab | 1 |
| **4** | UI 장식·아이콘 | 절차적으로 못 넘는 선. 생성 모델 축 | 없음 |
| **5** | 이펙트 확장(트레일·빔·참격) | 같은 축 | 없음 |
| **6** | 격자 자동 검출(FFT) | 지금은 내가 눈대중으로 `--size` 를 준다. 공개 방법 있음 | 없음 |

**1번이 먼저인 이유**: 도구가 있다고 **믿고** 있을 뿐 돌려본 적이 없다.
이 레포에서 그 믿음이 틀린 적이 여러 번 있다(도달 불가 도구 1,003줄 · 9-slice null · 팔레트 입력 없음).

## 측정이 내 순서를 두 번 뒤집었다

- "계단 정리가 AI 티의 핵심" -> **LoRA 경로는 이미 상용 범위**(cv 0.856 vs 0.52~0.89)였다
- "색군을 줄여야 한다" -> 캐스트에 걸면 **캐릭터 고유색이 섞인다**. 한 장당 수치였다

**새 축을 열 때 순서를 먼저 정하지 마라.** `dot-rules.mjs` 로 재고 나서 정해라.

## 수치가 통과해도 눈이 따로 필요하다

오늘 사람이 세 번 잡았다 — 흰색이 알파로 빠짐 · 발이 잘림 · 눈과 이빨이 뚫림.
**도구는 전부 "통과"였다.** 색군 제약도 dE 4.5 로 통과였는데 눈으로는 분명히 나빴다.
`pixel-contract` 는 "도트인가"를, `palette-force --verify-only` 는 "그림이 남았는가"를 본다.
**"좋은가"를 보는 도구는 없고 앞으로도 안 만든다** — 그게 review-loop 가 있는 이유다.

## 안 할 것 (범위 경계)

- **3D·시네마틱·사운드** — 목표 밖이다. `asset-3d-pipeline` 은 엔진 임포트 보조까지만
- **장르·엔진 특화 하드코딩** — CLAUDE.md 핵심 설계 원칙. 프로젝트 AGENTS.md 몫이다
- **"보기 좋은가"의 자동 판정** — 설계상 사람 축이다. 도구는 **틀린 것**만 잡는다
- **히어로 에셋의 완전 자동화** — 업계 합의도 우리 실측도 같다(48px 얼굴은 6x6px).
  다만 "사람이 그린다"가 아니라 **"모델이 그리고 사람이 고른다"** 로 푼다

## 기준은 실측으로 잡는다

목표 2("도트도 잘")의 "잘"은 취향이 아니라 숫자다. 이미 상용 도트 300장에서 뽑아놨다:

- 색 수 중앙값 22 (16~32 = 52%)
- **91% 가 반투명 픽셀 0%**
- lonely 9.1% (IQR 6.3~10.8) · flat 14.3% (IQR 11.1~18.4)
- **어두운 외곽선 없음** (27% 만 가장자리가 더 어둡다 — 내 가정이 틀렸었다)

새 축을 열 때도 같은 방식으로 간다: **레퍼런스를 실측 → 하드 게이트와 화풍 지표를 분리 →
게이트로 건다.** 한 건으로 좁게 박지 않는다([[feedback-gate-calibration]]).
